The first responder that shows its work.

Ryker is an AI teammate for on-call and infrastructure teams. It investigates alerts and questions against live evidence, shows where every answer came from, and prepares fixes as draft pull requests. And every risky action asks a person first.

How does it do that?

Four habits, enforced by Ryker, not left to the model.

It uses your tools

Repositories, metrics, logs, registries — whatever your team connects through Emisar’s governed, typed actions. There is no production shell: Emisar’s policy decides what runs and what waits for a person, and everything is audited.

It remembers

What the team said and decided, the subjects it keeps current, how past problems ended, and the facts your team confirmed — always as history to check, never as proof.

It checks itself

Ryker checks every answer before anyone sees it. An alert answer that only restates the symptoms goes back for more investigation, and a source no tool returned is dropped. In this very thread, one reply was sent back and corrected before delivery.

It learns, on the record

Background learning keeps what it knows current, with every earlier version and the messages it came from. Facts, preferences, rules and schedules change only when a person confirms a card — nothing about its behavior changes silently.

It understands you.

Behavior is shaped in plain words, and it changes only on the record.

Tell it how you want things

“Keep replies short in this channel.” “Always verify before claiming recovery.” Say it in words — Ryker turns it into a preference or guidance with an exact scope and expiry, shows it to you, and saves it only after you confirm. Or write instructions for every conversation, or for one channel, in the control plane.

It listens to feedback

React to a reply with an emoji, or just say what was wrong. Reactions become part of the conversation Ryker reads next time, and what you say can be recorded as feedback. Neither can ever authorize anything.

Everything Ryker does

One line per feature. Everything listed here works today.

In Slack — 14

The whole surface an on-call engineer touches.

  • Answers where you ask. Mention it in a channel or thread, or message it directly; the answer lands there, with no incident created.
  • Reads the conversation. Up to 20 recent messages from the thread or channel, not just the one that mentioned it.
  • Chooses when to speak. Stay silent, react, reply, or offer a room — and when you address it, it replies.
  • Alert answers with a verdict. Confirmed, likely, disproved or still unverified, with impact; real issues also get a mitigation and a lasting fix.
  • Incident rooms. One channel per incident, private by default, with a pinned card that updates in place.
  • Engineering tasks. A “Start task” button turns a request into an isolated working copy in the same thread.
  • Records built from facts. Timeline, evidence, handoff, and postmortem, from what was recorded rather than written by the model.
  • Channel setup in one click. Safe defaults on invite, or four questions: how to take part, which environment, what to do with alerts, who joins rooms.
  • Observe only. Reads a channel and records what it would have done, without posting a word.
  • App Home. What needs you, open incidents, work Ryker owes the team, and memory controls, without typing a command.
  • A message shortcut. “Investigate message” runs a read-only investigation even where Ryker is not listening.
  • The /ryker recovery command. Status, proactive, shadow, assignments, help — no model, and a private answer.
  • Files in, charts out. Screenshots, documents and PDFs in; up to five images or charts back, each with alt text.
  • Questions as buttons. When it needs a decision, the choices are buttons, not a paragraph to retype.

Beyond Slack — 3

The same Ryker, reached another way.

  • Chat. Talk to Ryker in the control plane, without Slack, through the same pipeline.
  • GitHub. Issue comments, pull-request reviews and inline comments; review comments on its own draft PRs go back to the task.
  • Signed webhooks. Grafana alerts, mapped JSON alerts, or any authenticated JSON, deduplicated by event.

Code and environments — 8

Where work runs, what it may change, and how a change reaches you.

  • Environments. A set of repositories plus an optional Emisar account; channels, webhooks and Chat each work in one.
  • One repository changes, the rest are read-only. A task picks which repository of its environment it changes.
  • A RYKER.md for every repository. Adding a repository proposes a pull request describing what Ryker learned about it.
  • Automatic checks. Finished changes are compared with the current repository, rebased, and run through your checks.
  • Draft pull requests only. The pushed tree must match the reviewed tree exactly, or nothing is published.
  • Follow-through. Checks, merges, and deployment or Terraform messages that name the exact PR, branch or commit.
  • Red CI goes back to the task. If checks fail on the published commit, Ryker corrects the work and updates the same PR.
  • Safe cleanup. Uncommitted work is never discarded; unmerged commits only once they are in a draft PR, or when you say so.

Memory and learning — 8

What it knows, where it got it, and how long that is good for.

  • Source excerpts. What a message actually said, with its source and time, kept even when Ryker stayed silent.
  • Topics. Background learning keeps one current understanding per subject, with every earlier version.
  • Conversation summaries. Where each conversation stands, so the next session picks up where it stopped.
  • Past cases. What a finished piece of work found and fixed, to check against when something similar happens.
  • Findings. Each conclusion an investigation reached, with its evidence, and whether it is explained yet.
  • Confirmed facts. Names, repositories and routes a person asked it to remember, saved only after they confirm.
  • Preferences, guidance and instructions. Check depth, reply detail, where to answer, and advice in your own words.
  • Memory review. Unused and repeated facts are flagged to keep, edit, merge or forget. Nothing edits confirmed memory silently.

Automation and governed action — 7

The parts that can change something, and the gates in front of them.

  • Rules. “When someone posts a Terraform plan here, review it” — confirmed on a card, paused or deleted any time.
  • Schedules. One-time and recurring runs in your timezone, never overlapping, confirmed before they exist.
  • Follow-ups. Work that waits for a time or an event, such as a merge, then picks the same request back up.
  • Emisar actions. Live checks and fixes go through Emisar’s typed actions. No free-form command reaches your infrastructure.
  • Approvals owned by Emisar. Slack links to the exact pending approval; the decision is made and audited in Emisar.
  • Watched runs. After approval, Ryker follows the exact run and continues in the same conversation.
  • Waiting is free. A paused request holds no model and no worker, and survives restarts.

Platform and trust — 10

What you run, and what you can check afterwards.

  • Docker Compose on one host. ./install.sh starts PostgreSQL, Ryker and a bundled worker.
  • One database. PostgreSQL holds every request, reply and wait; a restart resumes where it stopped.
  • Loopback by default. Publish only the signed GitHub and webhook paths; Slack needs no inbound port.
  • Encrypted credentials. Tokens are entered in the setup UI and stored encrypted, never in a file.
  • Isolated work. Tasks run in their own working copies, on a worker with its own private Docker daemon.
  • A timeline for every request. The exact briefing the model saw, every check, the reply, and what it cost.
  • Failures that say what to do. Each stopped item says whether a retry should work, and what its button does.
  • Usage and cost. By model, kind of work, channel and repository. Unmeasured is never shown as zero.
  • Backups with their keys. One command writes the database, the worker’s state and the keys to read them.
  • Signed releases. A cosign-signed checksum file and GitHub build provenance.

Built to be doubted

Ryker assumes you will check its work — and makes checking easy.

  • Every piece of evidence names where it came from.
  • Every request keeps the exact briefing its model received, for as long as you choose to keep it.
  • Ryker sends back answers that break its rules, and every check is on the request’s timeline — on a control plane you run yourself.
  • Silence is a feature: noise, duplicates and routine success notices get nothing.

Where your data goes

Your prompts go to one place: the model provider you configure, reached through Coop. There is no second model runtime and no direct provider client in Ryker. Slack messages, evidence, requests, and their timelines live in PostgreSQL on your host.

What it cannot do

  • Merge or deploy
  • Run untyped commands in production
  • Approve its own actions
  • Widen its own authority
  • Hide a failed check

These are not missing features. Each one is a boundary Ryker enforces or leaves to the system that owns it, and each one is the reason the rest can be trusted.
