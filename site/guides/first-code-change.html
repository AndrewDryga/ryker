From a Slack request to a reviewed pull request

Give Ryker a change your team needs. Follow the work in Slack, then review the code in GitHub.

1. Choose the repository

You need a running Ryker installation, a connected GitHub repository, and a Slack channel Ryker has joined. An active full member of the Slack workspace can start a code task.

If you manage the installation, open Work › Environments in the console. Add the repository with read/write access, then choose that environment for your channel under Work › Channels. Other repositories can stay read-only so Ryker can use them as context. If you do not have console access, ask a Ryker operator to set this up for you.

Choose a change with a clear result. The example below asks for an input-validation fix. Replace the repository, behavior and expected result with a change your project needs.

2. Ask for the change

@Ryker in your-team/your-repository, reject an empty email address when creating a user. Return the same validation error as other invalid inputs. Add a regression test and run the relevant tests.

Read the proposed task, then press Start task. That confirmation creates the writable work. If Ryker only explains the change, ask it to prepare the edit as a task.

Keep the conversation in that thread. Ryker uses a separate checkout, so your own working copy stays yours. If it asks a question, answer there; the task continues with your answer.

3. Follow the work

The task card updates as Ryker plans, edits and checks the change. If you have console access, open the task for its timeline and recorded checks. Otherwise, follow the card in Slack and ask an operator to investigate any failure you cannot resolve from the thread.

If the task waits, read the question or failure before asking it to try again. A missing dependency needs a different response from a failed test. For a worker or sign-in problem, use the troubleshooting guide.

4. Open the draft

Draft pull requests are off until an operator enables them in Integrations › GitHub. Once enabled, a confirmed task can open its own draft when the person confirming it named the repository and the automated review is clean. Otherwise, an operator uses Create draft PR.

Before publication, the worker rebases the change and runs the configured checks. A failing check or conflict stops publication. A missing check is reported as missing; it does not count as a pass.

The draft contains the reviewed change on a Ryker-owned branch. Open it in GitHub to review the diff and checks. You do not need access to Ryker’s console to review the pull request.

5. Review the change in GitHub

Read the diff and compare it with your request. For the validation example, check that empty input gets the expected error and valid inputs still work. Read the regression test and the actual check results, including checks that did not run.

Ask for a correction in the task’s thread or on the pull request when something is missing. For example:

Also handle an email address containing only spaces. Add a test for that case and keep the error response consistent.

Pull request comments return to the same task. Failed CI on the published commit can also send it back for a fix within the task’s scope.

Your team marks the pull request ready, merges it and releases it. Ryker follows the result in the original thread. For the full publication rules, see code changes and draft pull requests.

You’re done when

You can explain the diff, see which checks ran, and review the draft in GitHub.

Give it the next piece of work

Try a change that needs context from a second repository, or ask Ryker to review an existing pull request. To investigate a problem in a running service, follow the alert walkthrough.
