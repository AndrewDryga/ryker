Run it

Responder is one Go binary and one SQLite file on one host you control. There is no cluster, no broker, and no second datastore. This page walks the first hour: install, configure, connect Slack, prove it works, then let it into a channel.

Be honest with yourself first

This is a design-partner preview. It assumes an operator who is comfortable with a Unix host, a YAML file, a systemd unit, and a reverse proxy. There is no hosted option and no installer. If that is not you today, read what Responder is and come back.

What you need

  • A Linux or macOS host you trust, and Go 1.26 or newer to build from source — or a released binary.
  • Coop, running its local session API. Coop owns the model session, the isolated fork, and the box the agent runs in.
  • A model account Coop can sign into. Bring your own; several providers work, and you can list more than one.
  • A Slack workspace where you can create an app.
  • An observe-scoped API key for Emisar — the infrastructure authority Responder acts through — for live infrastructure evidence.
  • A TLS reverse proxy, only if you want to receive webhooks from outside the host.

1. Install the binary

From source, for your own user:

shell

make install
# writes ~/.local/bin/responder
# set INSTALL_DIR to put it elsewhere

For a service installation, build once and install it system-wide, then create a locked-down service account and directories. The repository ships the exact commands, plus systemd units in deploy/systemd/. Two units, deliberately: only the Coop unit gets the docker group, so the Responder process never holds it.

Release archives carry a signed checksum manifest and build provenance. Verify the manifest with cosign before you check the sums — comparing checksums against an unauthenticated manifest proves nothing.

2. Write the config

One YAML file. Below is a short illustrative shape, not a complete one — the repository ships config/responder.example.yaml with every key and a comment explaining why it exists.

responder.yaml · illustrative, not complete

version: 1
listen: 127.0.0.1:8080       # loopback is enforced, not advised
state_dir: /var/lib/responder

slack:
  bot_token_env: SLACK_BOT_TOKEN
  app_token_env: SLACK_APP_TOKEN
  team_id: T0123456789
  operators: [U0123456789]   # who may steer, approve, and publish
  default_repository: infrastructure
  channel_prefix: ems          # incident rooms are named ems-MMDD-...

coop:
  supervise: true              # one process; false uses the split units
  binary: /usr/local/bin/coop
  policies: /etc/responder/session-policies.yaml
  emisar_token_env: EMISAR_API_KEY

repositories:
  infrastructure:
    coop_policy: infrastructure-observe
    github: example/infrastructure  # Responder owns this clone

webhooks:
  grafana:
    kind: grafana
    auth: bearer
    secret_env: GRAFANA_WEBHOOK_TOKEN
    repository: infrastructure
    group_by_labels: [cluster, namespace, service]

Secrets never live in this file. Each one names an environment variable, and every configured secret must be at least 16 bytes. Use independently generated random values for the webhook secrets.

Declare a repository with github: and Responder owns the checkout: it clones into <state_dir>/repos/<owner>/<repo>, keeps it current with a fetch and a fast-forward every fifteen minutes, and never modifies the work tree. The GitHub credential stays host-side and reaches git as a per-invocation header — never a file, never an argument, never anything projected into the agent box. Use path: instead for a repository you maintain yourself or one that is not on GitHub. Exactly one of the two is required.

3. Create the Slack app

Create the app from deploy/slack-app-manifest.yaml. The manifest holds the complete supported event, scope, interactivity, and presentation configuration, and it enables socket mode — so Slack connects outward to you and you publish no request URL.

  1. Create the app from the manifest, and upload deploy/slack-app-icon.png.
  2. Install it to the workspace and take the bot token (xoxb-…) as SLACK_BOT_TOKEN.
  3. Create an app-level token with connections:write and use that xapp-… value as SLACK_APP_TOKEN.

Note

Slack does not accept socket-mode apps in its Marketplace; a published app needs public HTTP request URLs. That is a fine trade for a self-hosted tool, and it is worth knowing before you plan a distribution path.

4. Point Coop at a model

Write Coop’s private projection, then sign the agent account in to that same dedicated configuration:

shell

responder bootstrap-coop --config /etc/responder/responder.yaml
coop login codex@oncall

A session policy names one target, or an ordered ladder of up to four that may cross providers:

session-policies.yaml · illustrative

    target: [codex:gpt-5.6/medium@oncall, claude@oncall]

When a session hits a usage limit, Coop moves it to the next rung and re-delivers the same turn. A rate limit mid-incident costs a retry, not the investigation. Sign in on every rung — responder doctor checks all of them, not only the one sessions start on.

Responder never sends the Slack or Emisar tokens through Coop’s session API. bootstrap-coop writes the Emisar key into Coop’s owner-private environment file, and mcp.json refers to it by variable name.

5. Prove it works before Slack sees it

shell

responder doctor --config /etc/responder/responder.yaml

doctor checks the database, the Coop bootstrap content, your bot scopes, every configured operator and channel, an actual socket-mode handshake, and an authenticated Emisar catalog including the tools Responder depends on. It validates all of that without executing an infrastructure action. Then start it:

shell

responder serve --config /etc/responder/responder.yaml
curl -f http://127.0.0.1:8080/readyz

/readyz means more than “the process is up”: the database answers, Slack and Coop are ready, every scheduler lane has a fresh heartbeat, and no due or running work has exceeded the stall threshold. Health and metrics stay on loopback. They are unauthenticated, so do not publish them.

6. Invite it to one channel

Invite the bot to a channel. It introduces itself with three buttons rather than a form:

Use safe defaults
Mentions only, the deployment repository, in-place replies to app alerts, and no additional incident invitees.
Be proactive
The same, but it reads every message in the channel and decides for itself whether to speak.
Customize
Four questions.

The four questions are: how it should participate (mentions only, proactive, or shadow); which repository or repository set gives it code context; what to do with app alerts (reply here, offer an incident button, or open one automatically); and who else joins an incident room besides your configured operators, who are always invited.

The setup conversation lasts thirty minutes and prints its own expiry. The final card shows the normalized typed values and the safety boundary, and it opens with the words “Nothing is saved yet.” A configured operator has to confirm before anything changes. Say @Responder reconfigure this channel to run it again — that one phrase is read from plain text, so it still works when the model is unavailable.

Then try it. Mention it on something real:

slack

@Responder investigate elevated checkout latency in production

It replies in that thread and creates no incident. To get an incident room, ask for one in words, or press the button it offers you.

7. Send it alerts

The service listens on loopback. Publish only /v1/hooks/ through your TLS reverse proxy; the shipped nginx config returns 404 for everything else.

shell

curl -f \
  -H Content-Type: application/json \
  -H Authorization: Bearer $GRAFANA_WEBHOOK_TOKEN \
  -H X-Responder-Event-ID: grafana-delivery-123 \
  --data-binary @grafana-alert.json \
  http://127.0.0.1:8080/v1/hooks/grafana

Two route kinds carry alerts. Grafana routes read the payload natively: the alert fingerprint is the signal identity and groupKey is the preferred correlation key, with your configured labels as the fallback. Generic routes take a small dot-path mapping — event_id, status and title are required — and deliberately execute no jq, no CEL, no templates, and no user scripts. A third kind, change, records what changed without opening anything; see the change ledger.

Deliveries are deduplicated by the X-Responder-Event-ID header, or by a digest of the body when you send none. Reusing an event ID with different content is a 409, not a silent overwrite. Both auth modes are supported: a bearer token, or an HMAC signature over the timestamp, event ID and raw body with a five-minute window.

What this is not, yet

  • One workspace, one host. One Responder process, one state directory, one Slack credential pair, one Emisar identity per workspace. Sharing any of those across workspaces is unsupported.
  • One repository context per incident — or one repository set: one primary writable repository plus up to 32 read-only companions pinned at session creation.
  • No autonomous mutation. Model-proposed, inferred, and automatic operational changes are disabled. A configured operator asks for one exact action, and Emisar decides.
  • No hosted control plane. The web UI binds to loopback and has no accounts, because the loopback interface is the authentication.
