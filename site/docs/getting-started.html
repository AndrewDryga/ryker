Run it

Ryker runs as one Docker Compose project on a trusted host: the Ryker service, PostgreSQL, and a bundled Coop worker. This page is the shortest path from a checkout to a first answer in Slack.

What you need

  • A host with Docker and Docker Compose v2, plus OpenSSL, curl and tar.
  • A model account for the work itself. The installer signs in to Codex through Coop, or reuses an existing Codex sign-in on the host.
  • A Slack workspace where you can create an app from Ryker’s manifest.
  • A GitHub App of your own, installed on the repositories Ryker should read and change.
  • Optionally, an Emisar account, so Ryker can check and act on running systems.

Install

shell

git clone https://github.com/AndrewDryga/ryker ryker
cd ryker
./install.sh

The installer:

  • creates .ryker/, readable only by you, and in it compose.env;
  • on the first run, generates the database password and Ryker’s encryption keys, and reuses them on every later run;
  • builds and starts PostgreSQL, Ryker, and the bundled worker with its private Docker daemon;
  • asks you to sign in to the model account, unless the worker already has one;
  • waits until Ryker is healthy, ready, and running the exact version it built, then prints the setup address.

Running it again keeps the same keys and data.

Credentials never go in a file

Slack, GitHub, Emisar and webhook credentials are entered in the setup UI and stored encrypted in PostgreSQL. They never belong in Compose or in .ryker/compose.env, which holds only the version, the listening addresses, and the generated password and keys.

Set it up

Open the address the installer printed, http://127.0.0.1:4321/setup. Setup has six steps, one open at a time, each with what it needs and one button:

  1. Connect Slack. Create the app from deploy/slack-app-manifest.yaml, generate an app-level token with connections:write, install the app, and paste the app token and the bot token. Then choose who can manage Ryker.
  2. Connect the GitHub App. Enter its App ID and private key, then paste the callback address Ryker shows into the App’s webhook settings. GitHub has to reach that address, so publish that one path through HTTPS (how).
  3. Add repositories. Pick the ones Ryker should work in, or add every repository the App can reach. Ryker copies each one, reads it, and proposes a RYKER.md describing what it learned, in a pull request you can review.
  4. Invite Ryker to a Slack channel.
  5. Choose that channel’s environment. A channel Ryker joins starts in the default environment, which adding a repository created, so this step usually checks itself off.
  6. Send one real request in Slack and get the answer.

Ryker notices the Slack steps on its own and checks them off. Emisar is the one recommended extra: it never blocks setup, but without it Ryker can only tell you what to run. The first Emisar account you connect is given to every environment that has none.

Each step has its own page afterwards: integrations under Integrations, environments under Work › Environments, and models, retention and prices under Settings. What an environment is.

Check it is running

shell

scripts/compose.sh status
curl --fail http://127.0.0.1:4321/healthz
curl --fail --include http://127.0.0.1:4321/readyz

/healthz means the process can use PostgreSQL. /readyz means its runtimes are alive and due work is making progress, and its x-ryker-version header names the exact version that is running.

Then open Chat at http://127.0.0.1:4321/conversations to talk to Ryker without Slack. It goes through the same pipeline, so it is the quickest way to see a request, its timeline and its cost end to end.

What stays off until you turn it on

Background learning is on by default. Proactive participation, opening pull requests, scheduled reports and anything destructive stay off until someone turns them on.

The UI keeps four facts apart, and one does not imply the next: a setting can be saved, the running service can have applied it, an integration can be connected, and a real request can have succeeded through it.
