Working in Slack

Slack is where most of Ryker’s work happens. This page covers how to ask it something, how it decides whether to speak, what an alert answer contains, and the controls on its cards.

Asking it something

Mention it in any channel it has been invited to. It investigates and replies in that thread, and creates no incident.

slack

@Ryker investigate elevated checkout latency in production

The reply follows you: a top-level mention is answered at the top level, a mention inside a thread is answered in that thread. A direct message to Ryker works the same way and needs no channel setup.

Ask in your own words. The model works out what you meant and Ryker carries it out. No sentence is matched against a list of phrases, so ordinary conversation in a channel is never mistaken for a command. The one request Ryker reads as plain text is @Ryker reconfigure this channel, so that channel setup still works when the model is unavailable.

What it reads

Ryker reads the conversation around your message, not just the message: by default up to 20 earlier messages from the same thread, including its first message, or from the channel before a top-level message. To point it at another conversation, paste the link and ask; it can read a linked message when it needs to.

Staying in the conversation

After Ryker answers, nearby follow-ups in the same place are read without another mention for the next 30 minutes. In a task thread, every reply continues the task. In an incident room, configured operators can talk to Ryker anywhere without mentioning it.

Setting up a channel

Invite Ryker with /invite @Ryker. It posts one welcome message, and safe defaults are already in effect: it replies only when mentioned (the default for new channels, which you can change), works in the default environment, investigates app alerts in their own thread, and invites nobody extra to incident rooms. Nothing needs a click.

The welcome’s buttons change that in one step: Be proactive or Mentions only, and Customize for a short setup conversation. Customize asks four questions, and explains each option before you choose:

  1. How to take part: Mentions only, Be proactive, or Observe only.
  2. Which environment the channel’s work uses, or No environment, which answers without any repositories or Emisar.
  3. What to do with app alerts: investigate in the alert’s thread, offer a choice between the thread and an incident room, or create a room automatically.
  4. Who else to invite to incident rooms. Configured operators are always invited.

A final summary shows exactly what will be saved, and nothing changes until a configured operator saves it. A stale or copied setup button is refused. You can also choose a channel’s environment on its page in the control plane, and /ryker status shows the channel’s current settings privately, with a Configure channel button.

When it speaks

In a channel set to Mentions only, Ryker answers when it is mentioned or messaged. In a proactive channel it reads every message from people and from monitoring apps, and chooses one response:

Stay silent
Noise, routine success or recovery notices, duplicates, and people talking to each other. The decision is still recorded.
React
One emoji, when acknowledgement helps but a reply would interrupt.
Reply
An answer where the person is speaking.
Offer an incident room
For a problem that may need coordinated work. Nothing is created until an operator chooses.
Offer a task
A Start task button, when someone explicitly asks for a change to code.
Open an incident room
Only for a credible, unresolved alert from a monitoring app, when the channel’s alert setting says so. Asking for a room in words gets you the offer.

A person’s message never becomes an incident on its own. When you address Ryker, it replies.

Observe only

Set a channel to Observe only and Ryker reads it, learns from it and records what it would have done, but posts nothing. Use it to see how Ryker would behave in a room before you let it speak there: /ryker shadow on.

Alert answers

When a monitoring app posts, Ryker does not repeat the alert back to you. It checks what your repositories say should be running against fresh live evidence, through Emisar or your monitoring tools, and answers with a verdict: confirmed, likely, disproved or still unverified, with the impact. A confirmed or likely issue also gets an immediate mitigation and a lasting fix.

An answer that only restates the symptoms is sent back to the same run for more investigation before anyone sees it. A Terraform review needs the exact plan, from the message or a read-only tool; Ryker does not guess it from the repository.

A Sources footer lists only links that a tool actually returned during the same investigation. A link the model wrote itself is left out.

Incident rooms

An incident gets its own Slack channel, named <prefix>-MMDD-<title>-<id> with your configured prefix (inc by default). Rooms are private by default. Configured operators are always invited, plus anyone the channel’s setup adds.

A room is opened in one of two ways: a configured operator presses Create incident room on Ryker’s offer, or the channel’s alert setting opens one for a credible unresolved app alert. Ryker makes the offer when a problem needs coordinated work, or when someone asks in words (“open an incident for elevated checkout latency”). The offer’s other choice, Investigate, runs the same investigation in the thread, with no room and no invitations.

The pinned card is the room’s current state: the alert, what the investigation has established so far, anything that needs a person, and only the controls that work right now. It updates in place. The room keeps the environment of the conversation it was opened from.

Archiving the channel pauses the investigation until someone unarchives it. Deleting it closes the room, and Ryker says so in the alert’s thread; a reply it still owed the room goes there instead. By default a workspace can have 25 rooms open at once.

Engineering tasks

When someone explicitly asks for a change to code, the reply can carry a Start task button. Any active full member of the workspace can press it. Nothing writable exists until then.

The task runs in an isolated working copy, in the same Slack thread, inside the conversation’s environment. It changes one of the environment’s repositories, the one the task names, and reads the others without changing them. A conversation with no environment has no repository a task could change. Later replies in the thread continue the task without a mention; messages elsewhere in the channel stay out of it.

The task card lists its stages: Workspace setup, Planning, Implementation, Self-review and checks, Draft PR, CI, and Review and merge. When the changes are ready, Ryker checks them on its own: it compares them with the current repository, rebases, runs your configured checks, and says whether the result is ready for review.

Then a draft pull request. When Ryker is allowed to open pull requests (a setting on the GitHub integration), a task whose confirmer named that repository opens its draft itself once the review is clean. Otherwise a configured operator presses Create draft PR. After that the card offers Open PR and Check delivery. If CI fails on that exact commit, Ryker corrects the work within the task and updates the same pull request. Review comments on the pull request in GitHub go back to the same task. How publication works.

Diffs are read in the control plane, not in Slack. Stop current run cancels only the active run; the working copy stays. Closing a task keeps any uncommitted or unpublished changes. Only configured operators can publish, stop, close, or discard work.

Records on every card

Every work card’s menu holds its records: Timeline, Evidence, Handoff summary, and on an incident Postmortem draft. On an incident card, Open evidence is a button of its own, because there the findings are the point.

All of them are built from what Ryker recorded: the alert, the runs, what people did, Emisar approvals and their results, and the draft pull request. The model never writes a timeline. The postmortem draft can be built at any time, including after the incident closed, and it does not invent impact, root cause, owners or corrective actions.

Progress, questions and files

While a request is in progress, Slack’s own status line says where it stands in plain words (queued, deciding how to respond, working, preparing the response) until it is answered, settled silently, handed off, or stopped. When Ryker needs a decision from you, it asks with buttons: up to five choices as buttons, six to ten as a list with Submit answer. A typed reply works too.

You can attach up to four files to a message, 8 MiB in all: screenshots (PNG, JPEG, WebP, GIF), text, Markdown, CSV, JSON, YAML, or PDF. Ryker checks each file’s type and size before the model sees it, and refuses content it cannot verify rather than guessing.

Replies use Slack’s Markdown, with headings, lists, tables and code blocks. Buttons, mentions and approval links are always Ryker’s own, never the model’s. A reply is one message; posting somewhere else as well needs the requester to confirm it.

Images and charts

Ask for a chart or an image and Ryker can return up to five in the same thread, 8 MiB in all, each with a title and alt text, when the configured model has a suitable tool. A chart is a picture of data, not evidence: the observations behind it must be sourced on their own.

Reactions and feedback

Ryker may add one reaction to acknowledge a message. A reaction never claims that something was verified, approved or fixed.

Reactions people add to Ryker’s messages are part of the conversation it reads next time: which emoji, and who. They never start work or authorize anything. To say what was wrong, just tell it; Ryker can record that as feedback.

App Home and the shortcut

App Home answers “does anything need me?”: open incidents, active and failed work, what Ryker owes the team, and saved memory, with rows that jump to the exact thread. Operators manage schedules, rules and memory there too. The Messages tab offers suggested prompts: production health, explain an alert, and open work.

Any message has an Investigate message shortcut. It runs the same read-only investigation and replies in that message’s thread, even in a channel where Ryker is not listening.

The /ryker command

This is the emergency kit, and it is small on purpose:

slack

/ryker status
/ryker proactive on|off|inherit # add `global` for the workspace default
/ryker shadow on|off|inherit
/ryker assignments [list|pause|resume|delete]
/ryker help

It is what has to work when nothing else does. No model runs, no worker is needed, and the answer is private to whoever typed it. Only configured operators can use it.

A channel’s own setting wins over the workspace default. inherit clears the channel’s own setting, so it follows the default again. Everything else lives on the cards, in App Home, in the control plane, or in conversation.

Who can do what

Configured operators are the people chosen on the Slack integration page as the ones who can manage Ryker.

ActionWho
Ask a question, get an investigationAny active full member of the workspace
Start a task, work in its thread, review its changesAny active full member of the workspace
Steer an incident, approve an incident offerConfigured operator
Save a fact, preference, rule or scheduleConfigured operator
Publish a draft PR, stop, close, or discard workConfigured operator
Use /rykerConfigured operator
Anything at allNot guests, bots, deactivated accounts, or Slack Connect users

Changes to running systems are not on this list because Ryker does not decide them: they go through Emisar, whose policy decides what runs and who must approve it. See approvals.
