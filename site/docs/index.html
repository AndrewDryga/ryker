What Ryker is

Ryker is an AI teammate for on-call and infrastructure teams. It answers questions, investigates alerts, and prepares code in Slack, GitHub and its own chat, and it keeps a full record of how it reached every answer. This page is the whole mental model. Five minutes, four ideas.

Status

Design-partner preview. It runs in production on the author’s own infrastructure. It assumes an operator who is comfortable running Docker Compose on one host.

The shape of it

Ryker runs as one Docker Compose project on a host you control: the Ryker service, PostgreSQL, and a bundled Coop worker with its own private Docker daemon. It connects to Slack over Socket Mode, so Slack needs no inbound port. It reads your repositories to learn what your systems are supposed to look like, checks that against live evidence through Emisar, the infrastructure authority, and then says what it found.

The model runs inside Coop, which owns the isolated session and the working copy the model works in. You bring your own model account. Ryker has no second model runtime and no direct provider client.

Four owners, and the split is the point:

ConcernOwner
Conversations in Slack, GitHub, Chat and webhooks, the durable record, cards and deliveryRyker
The model session, the isolated working copy and box, the model account, what each kind of work may runCoop
Infrastructure identity, policy, approval, execution and auditEmisar
Merge, signing, deploymentA person, outside all three

Environments

An environment is where Ryker works: a set of repositories, all of which work in it can read, and at most one Emisar account. Slack channels, webhook sources and Chat conversations each work in one environment.

A task that changes code picks one repository of its environment to change, and the others are mounted beside it read-only. The first repository is the default choice. Adding a repository puts it in the default environment, and creates one named Default when there is none, so a new installation needs no extra step. A channel can also choose No environment: Ryker then answers there without any repositories or Emisar.

The environment’s Emisar account decides whether work there can act on running systems. With one, Ryker sends the actions it wants to run to Emisar, where a person approves each risky one. Without one, Ryker can only tell you what to run.

Idea one: every request has a timeline

Everything Ryker accepts, whether a question in a thread, an alert at 3am, a GitHub comment or a scheduled morning check, becomes a request recorded in PostgreSQL. There is no second path and no lightweight path.

A request moves through four stages you can see: intake, routing, work and answer. Because the record lives in the database rather than in a process, a request survives a restart. Work that has to wait, for an approval, a merge or a set time, pauses without holding a model or a worker and picks the same request back up later.

Every request has a timeline on the control plane you run yourself: the message that started it, how Ryker decided what to do, the exact briefing sent to the model and the answer it got back, each check, the reply, and what it cost. See the control plane.

Idea two: answers rest on evidence

Ryker does not write a paragraph and then look for support. While it investigates, it records what it observed, and the answer is built from those records.

Each piece of evidence names its source (a repository, Emisar, monitoring, Slack or another tool) and what was observed, and can carry when it was observed, how fresh it is, and a confidence of high, medium or low. Evidence can support a claim or contradict it, and newer evidence can replace an older record instead of quietly overwriting it.

Conclusions are saved as findings, each with the evidence behind it and a state in plain words: explained, expected, out of scope, or not explained yet. A question that is still open says so. It is not rounded up to an answer.

Idea three: Ryker checks the model’s answer

The model’s answer is an input, not a result. Before anything is posted, Ryker checks it against the rules for that kind of answer, and an answer that fails goes back to the same run with a correction.

An alert answer that only restates the symptoms is sent back for more investigation. A source link that no tool actually returned is dropped. Buttons, mentions and approval links are always Ryker’s own, never text the model wrote.

Every check is a step on the request’s timeline, including the ones that failed. A bad first answer is part of the record, not something scrubbed out of it.

Idea four: it chooses when to speak

Ryker does not have one volume knob. In a channel where it is proactive, it picks one response for every message it sees:

Stay silent
Routine noise, success notices, duplicates, people talking to each other. The kind of message a teammate would read and say nothing about. The decision is still recorded.
React
One emoji, when a reply would be noise but silence would be rude.
Reply
An evidence-backed answer, where the person was speaking.
Offer an incident room
A button, for a problem that may need coordinated work. Only a configured operator can press it.

A person’s message never becomes an incident on its own. A room opens only from a credible, unresolved alert under the channel’s setting, an operator’s explicit request, or an operator accepting the offer. When you address Ryker directly, it replies. More on this.

What it cannot do

This list is a feature. Each line is a boundary Ryker enforces or leaves to the system that owns it, not an unfinished corner.

  • It cannot merge, deploy from repository changes, or sign a commit.
  • It cannot run a free-form command on your infrastructure. There is no shell path: actions go through Emisar, whose policy decides what runs and who approves it.
  • It cannot approve its own action. Approval happens in Emisar, by a person.
  • It cannot change a read-only repository, push an arbitrary branch, or open anything but a draft pull request.
  • It cannot save a fact, preference, rule or schedule on its own. It can only propose one for a person to confirm.
  • It cannot discard uncommitted work. Not through cleanup, not through Slack, not through the control plane.
  • It cannot widen its own reach. A payload, a reaction or a model answer never adds a repository or an Emisar account: the environment decides those, and the worker’s policy decides what each kind of work may run.
