What Ryker is

Ryker is an AI teammate for engineering and operations. Ask it to investigate a problem, review a pull request, or prepare a fix in Slack, GitHub or its browser chat. It keeps the conversation and the work together.

Start with a question about a repository. Add alerts, scheduled checks and saved team guidance as you need them. You choose where Ryker participates, what it can access, and which changes need your approval.

Install Ryker to try it with your team, or read Working in Slack if your team already has it.

How the three tools work together

Ryker runs on a host you control with Docker Compose. It connects to Slack over Socket Mode, so Slack needs no inbound port. You bring the model account and connect the repositories and tools it should use.

ToolIts part in the work
RykerReads the conversation, manages the task, and brings the findings and progress back to your team. Sets which repositories and tools each task may use.
co:opRuns the model in a container and gives it a separate working copy of the code. Enforces the task’s access and execution limits.
EmisarConnects the work to running systems. Controls access, approvals and execution, and keeps a record of actions.

For example, Ryker can investigate a failed deployment through Emisar, prepare and test a fix in co:op, and open a draft pull request. Your team reviews and merges the change, then deploys it through your usual process.

The installation includes PostgreSQL and a co:op worker with its own private Docker daemon. The model runs inside co:op; Ryker coordinates its work. What runs on your host.

Choose its repositories and tools

An environment groups the repositories and optional Emisar account a conversation can use. Give an engineering channel access to the code it needs, and an on-call channel access to the systems it supports. Slack channels, webhook sources and Chat conversations each use one environment.

A task that changes code picks a repository marked read/write in its environment; read-only repositories are available as context beside it. The first repository is the default choice. After adding a repository, choose it under Work › Environments to make it available to work. A channel can also choose No environment: Ryker then answers there without any repositories or Emisar.

The environment’s Emisar account gives Ryker access to running systems under that account’s policy. Actions that need approval wait for a person in Emisar. Without an account, Ryker can explain a proposed infrastructure change but cannot carry it out.

Follow a request from start to finish

Open Activity in the console to see what people asked and where each request stands. Questions, alerts, GitHub comments and scheduled checks all have a recorded timeline.

The timeline follows four stages: intake, routing, work and answer. A request survives a restart. When it waits for an approval, a merge or a set time, it releases its model and worker, then continues when the wait is over.

Open a request to see the message that started it, why Ryker responded, what it sent to the model, the checks and reply, and the measured or estimated cost. Read a request’s timeline.

Check the evidence behind an answer

Ryker records what it observes while investigating. Its answers link back to those records, so you can inspect the source, ask a follow-up, or challenge a conclusion.

Each piece of evidence names its source (a repository, Emisar, monitoring, Slack or another tool) and what was observed, and can carry when it was observed, how fresh it is, and a confidence of high, medium or low. Evidence can support a claim or contradict it, and newer evidence can replace an older record instead of quietly overwriting it.

Conclusions are saved as findings, each with the evidence behind it and a state in plain words: explained, expected, out of scope, or not explained yet. A question that is still open says so. It is not rounded up to an answer.

See how an answer was checked

Before posting, Ryker checks the model’s answer against the requirements for that kind of work. If a check fails, it sends a correction to the same run.

An alert answer that only restates the symptoms is sent back for more investigation. A source link that no tool actually returned is dropped. Buttons, mentions and approval links are always Ryker’s own, never text the model wrote.

Every check is a step on the request’s timeline, including the ones that failed. You can inspect the original answer and the correction.

Choose when it joins in

Keep a channel on Mentions only, let Ryker Be proactive, or choose Observe only to see what it would do without letting it post. When proactive, it can:

Stay silent
Routine noise, success notices, duplicates, people talking to each other. The kind of message a teammate would read and say nothing about. The decision is still recorded.
React
One emoji to acknowledge a message without interrupting.
Reply
An evidence-backed answer, where the person was speaking.
Offer an incident room
A button, for a problem that may need coordinated work. Only a configured operator can press it.

A person’s message never becomes an incident on its own. A room opens only when a configured operator presses Create incident room on Ryker’s offer, or when the channel is set to open one for a credible, unresolved alert. When you address Ryker directly, it replies. More on this.

What stays in your hands

Your team controls access, publication and changes to running systems:

  • Merge and release: Ryker prepares draft pull requests. Your team merges, signs and deploys the code.
  • Infrastructure access: actions go through Emisar’s policy. A person approves requests that need approval; Ryker has no direct infrastructure shell.
  • Repository access: you choose which repositories a task may read or change. Publication uses a Ryker-owned branch.
  • Saved behavior: facts, preferences, rules and schedules need a person’s instruction or confirmation. An operator’s explicit correction can become guidance without a second click.
  • Retained work: uncommitted changes are kept through task closure and cleanup. Discarding unpublished commits requires an operator’s decision.
  • Task boundaries: Ryker fixes the permitted repositories, tools and execution limits before work starts; co:op enforces them. Messages and model answers cannot expand that access.
