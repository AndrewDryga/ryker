Memory and recall

Ryker remembers a lot: what a channel said and decided, how a past problem ended, and what your team asked it to keep in mind. None of it is ever treated as proof of what is true right now. This page is about that distinction, because it is the one that keeps memory useful instead of dangerous.

Memory is never proof

When sources disagree, the order is fixed. The current request, Ryker’s safety rules, fresh live evidence, the current repository content and Ryker’s configuration all come before anything remembered.

Memory is a hint about where to look, not a reading. It never proves current health, a deployment or an approval, never carries a credential, and never gives Ryker permission to act.

Reading and learning are separate

Deciding whether to reply and deciding what to remember are two different jobs. Ryker keeps what a message actually said even when it chooses to stay silent, or when a channel is set to observe only.

Background learning, which is on by default, then reads those messages in small batches and keeps useful subjects up to date: a rollout decision, an intended configuration, an unresolved problem. Ordinary chatter can produce no memory at all, and “nothing to change” is a normal outcome. Learning never sends a reply, and it can be switched off at once under Memory › Learning; messages then wait, and nothing already learned is lost.

A subject keeps one identity and a history of updates. A new title is not a new subject, and two incidents that share a service name are not the same incident. Learning changes what Ryker understands, never what it is allowed to do.

What it keeps

Source excerpts
What a message actually said, with where it came from and when. Available before background learning catches up, and not another model summary.
Topics
The current understanding of a useful subject, linked to the messages it came from, including corrections and open questions. Every earlier version stays in the topic’s history.
Conversation summaries
Where each conversation stands, written when work is accepted, so a later session can pick it up. Older summaries fold into weekly rollups without another model call.
Past cases
When work finishes, a compact record of it: the problem, the cause when one was actually established, what was tried, how it ended, and links to the sources. A case has no routine expiry, so a similar problem a year later can start with last year’s record, as history to check.
Confirmed facts, preferences and guidance
What people explicitly asked Ryker to keep. Background learning cannot change them or turn them into permission.

Topics and conversation summaries are under Memory › Learned, confirmed facts under Memory › Facts, and the conclusions of investigations, each with its evidence, under Memory › Findings.

How it recalls

Each new request gets a small selection of what it is allowed to see: relevant facts and guidance, recent excerpts, and summaries of related conversations. When that is not enough, the model can search memory further, by text, kind, source and date, page through the results, and follow an excerpt back into its original conversation.

Results are historical context. Private-channel context stays in its own scope, and anything from another channel requires current membership. A past case is advice about what worked once, never proof that this incident has the same cause, and never permission to repeat the fix.

Facts people confirm

You can ask Ryker to remember a fact, such as what a service is called or which repository holds it, or open-ended guidance such as “when explaining a fix to me, start with a simple summary.”

Ryker shows the exact value, where it applies and when it expires on a card, and nothing is saved until a configured operator confirms it. When Ryker asks an operator a question and says the answer will be remembered, that answer is saved as a fact without a second click. The model cannot write a fact on its own.

A fact applies everywhere, to one repository, or in one channel, and the row says which. In a channel, ask Ryker “what do you remember here?” to see what it would use.

Preferences and guidance

Preferences are typed defaults, from a closed list of three:

Check depth
quick, standard or deep, for example “when I ask about infrastructure health, always do a deep check.”
Reply detail
concise, standard or detailed.
Where to reply
follow the conversation, prefer a thread, or prefer the channel.

Each is set for one person, a channel, a repository or the workspace, and the closest one wins in that order. Where to reply has no repository setting, because a repository does not have an opinion about where to answer.

Guidance is advice in your own words. Personal guidance follows the person who gave it across channels; channel and workspace guidance records a team convention. Either way it is advice: it cannot start work, open an incident, approve an action, or count as evidence. Preferences and guidance are listed under Instructions, where each can be paused, resumed or deleted.

Instructions

Instructions tell Ryker how to work, in your own words, and they are written directly in the control plane rather than confirmed in conversation. One field applies to every conversation; each channel can add its own on its page, and where the two disagree, the channel wins. Each holds up to 2,000 characters.

Every new request carries a snapshot of the instructions that applied when it started; work already running keeps what it started with. Instructions never give Ryker permission to do more, and the model cannot edit them.

Keeping memory honest

Memory that nobody checks becomes memory nobody should trust. A scheduled review flags two things:

Unused
A fact nobody updated, recalled or reviewed in the last 30 days.
Repeated
The same fact or guidance saved more than once in the same place.

Flagged facts appear in App Home and under Memory › Facts, where you keep, edit, merge or forget each one. Forgetting erases the value. The review never silently edits what people confirmed, and a removed or replaced value is not copied into the audit record.

A topic that lost a message it was learned from is marked as not used, and Ryker stops relying on it until you rebuild it from messages you choose. The Learned page shows the exact request and answer behind every update.

How long it lasts

Conversation memory is kept for 90 days by default, set under Settings › Data retention. Editing or deleting the original message, or losing access to it, can make what was derived from it unavailable sooner, and reading a memory does not renew it. The memory pages show where each item came from, when it changed and when it expires, separately.

Facts that apply everywhere do not expire on their own; other facts end at their own expiry, or once they go unused for as long as conversation memory is kept. Past cases have no routine expiry, but deleting the original message erases the text of every case built from it.
