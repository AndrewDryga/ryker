Running Ryker

Use the Compose helper to check Ryker, upgrade it, and protect its data. The sections below cover routine operations, remote access and recovery.

What runs on your host

The Compose project ryker includes PostgreSQL (database), Ryker (ryker), the bundled co:op worker (ryker-coop), and the worker’s private Docker daemon (ryker-coop-docker). Data lives in named volumes. The owner-only .ryker/compose.env holds image pins, listening addresses and the keys generated at install.

Voice transcription and search by meaning run in separate CPU model services beside Ryker. Together their images take about 4 GB and they use about 3.5 GB of memory; the first build downloads about 2.8 GB. If a model cannot start, Ryker reports it and continues with reduced functionality. The model operations reference covers their settings and alternatives.

PostgreSQL keeps requests, work, pending replies, schedules, approvals and memory. Restarting the service resumes pending work. Back up both the database and the keys that decrypt its stored credentials.

Day to day

Choose the command for the action you need. Each uses the same Compose project and environment file.

CommandWhat it does
scripts/compose.sh statusShow the project’s containers and their state.
scripts/compose.sh logsRead the service logs.
scripts/compose.sh stopStop the services and keep their data.
scripts/compose.sh startStart the services using the pinned images.
scripts/compose.sh restartRestart the project’s services.
scripts/compose.sh model-loginSign the worker in to its model account, Codex by default, and restart only the worker.
scripts/compose.sh sign-inPrint a single-use console sign-in link.
scripts/compose.sh uninstallRemove containers and the network while keeping volumes, data and keys.

Upgrade

Upgrades build from your checkout. Move it to the published commit or release you intend to run, then make a backup and upgrade:

git pull --ff-only
scripts/compose.sh backup
scripts/compose.sh upgrade

The checkout must be clean. When it has an origin, the commit must be present on that remote’s main. The helper derives the version and image tag from the commit or annotated release tag and updates .ryker/compose.env; you do not need to edit those pins.

Upgrade builds Ryker, stops the running service, runs migrations with the new image, and starts the replacement. It checks health, readiness and the exact running version. If migration fails, Ryker stays stopped: restore the backup you took before the upgrade.

The running bundled worker and remote workers keep their current versions. To move the bundled worker to the co:op revision this checkout specifies, run:

scripts/compose.sh worker-upgrade

This prepares the new worker before replacing it, keeps its model sign-in, and waits for active commands. start, restart and restore use already-built images. The upgrade reference covers remote installs and automatic upgrades.

Deploy a commit

From a checkout, scripts/deploy.sh puts the current commit into production:

shell

scripts/deploy.sh
  • It refuses a dirty tree, and a commit that is not main’s unless you pass --allow-not-main on purpose.
  • It builds the image from a clean copy of the commit, so nothing git does not know about reaches it.
  • After the build succeeds, it pauses Ryker and backs up the database and encrypted state into .ryker/backups/. It runs migrations with the new image before replacing the container.
  • It replaces only the ryker container. PostgreSQL, the bundled worker and its Docker daemon keep running.
  • Only once health, readiness and the exact version check out does it pin the new version in .ryker/compose.env.

After Ryker is ready, the script builds and starts the voice and search models, replacing only those whose image or settings changed. A model that fails to start is reported without taking Ryker down.

If the new version fails, the script prints the container’s last log lines, stops the unverified replacement and leaves the previous version pinned. Check whether the failed release migrated the database before starting the previous image; restore the pre-deploy backup first if it did.

Backup and restore

shell

scripts/compose.sh backup
scripts/compose.sh restore .ryker/backups/ryker-YYYYMMDDTHHMMSSZ.tar.gz

A backup is an owner-only archive under .ryker/backups/: the PostgreSQL dump, Ryker’s private state, the worker’s sign-in and identity, and the generated environment needed to decrypt stored credentials. Keep a protected copy away from the host.

Restore checks that the archive’s keys match an existing installation. On a new installation it restores the archived keys, then the database. It pins and starts the version the backup was taken on, whose image must already be available, and checks that exact version. Keep the original keys: generating new ones cannot recover an encrypted database.

Destroy

Stopping Ryker is recoverable. Deleting its volumes and keys is not, so it takes an explicit phrase:

shell

RYKER_DESTROY_CONFIRM=delete-ryker-data scripts/compose.sh destroy

This removes the Compose volumes and the generated environment. Without a backup, the stored credentials and history cannot be recovered.

Network access and sign-in

Published listeners bind to 127.0.0.1. Keep those bindings local and use a tunnel or HTTPS reverse proxy when another machine needs access.

PortPurposeRemote access
4321Console, health and readinessAn SSH tunnel, Cloudflare Tunnel or Tailscale Serve. The console requires sign-in.
4319GitHub App eventsOptionally expose /v1/github through HTTPS. Ryker also retrieves App deliveries every 30 seconds.
4320Signed webhooksExpose only /v1/hooks/<source> through HTTPS when an external sender needs it.

Slack uses an outbound Socket Mode connection and needs no public listener. PostgreSQL and the bundled worker’s connection stay private. /metrics can be read without signing in at a loopback address; at a published address, it requires a signed-in user. Health and readiness are readable by anyone who can reach their listener.

To access the console on a remote host through SSH, replace the host name and run this on your own computer, then open http://127.0.0.1:4321:

ssh -N -L 4321:127.0.0.1:4321 user@your-ryker-host

For a shared HTTPS address, point a tunnel at http://localhost:4321. Set RYKER_CONTROL_PUBLIC_URL in .ryker/compose.env to that address, then run scripts/compose.sh start. Ryker’s links will use it. The Cloudflare setup guide includes optional Access integration.

People sign in using /ryker sign-in in Slack, Open the console in App Home, an invitation from Settings › Access, or a link from scripts/compose.sh sign-in on the host. Everyone signed in has full access to the installation. Sign-in methods and expiry.

For direct webhook delivery, the supplied Nginx configuration exposes the signed ingress paths and returns 404 elsewhere. Configure their external addresses with RYKER_GITHUB_PUBLIC_URL and RYKER_WEBHOOK_PUBLIC_URL, then run scripts/compose.sh start. The network reference also covers the trusted container peer if your Docker runtime reports a different forwarding address.

Health and recovery

EndpointMeaning
/healthzThe process can use PostgreSQL.
/readyzIts runtimes are alive and due work is making progress. The x-ryker-version header names the running version.
/metricsQueue, delivery, worker placement and retention measurements.

When readiness fails, check scripts/compose.sh status, then scripts/compose.sh logs. In the console, open the stopped request and the Failures page: they say what stopped and whether a retry should work. Do not edit database rows by hand; the retry controls keep the checks that make a retry safe.

What survives a restart

PostgreSQL holds the inputs, the work, the replies waiting to be delivered, follow-ups, schedules, approvals, memory and history, so a restart picks pending work back up where it stopped. Waiting on an Emisar approval, a merge or a set time holds no model and no worker.

Credentials are stored encrypted in the same database. The keys that decrypt them are generated once at install and kept in .ryker/compose.env and in every backup.

Retention

Older data is deleted on its own. The limits are set under Settings › Data retention, and the defaults are:

Kind of dataKept for
Prompts, replies and tool activity30 days
Finished work30 days
Request history30 days
Audit trail30 days
Conversation memory90 days

Keep the audit trail at least as long as request history, request history at least as long as finished work, and finished work at least as long as its prompts, replies and tool activity. Ryker enforces that order. Shortening a limit deletes older data, so the page asks for confirmation.

Nothing still in use is cleaned up underneath you. Open follow-ups, blocked work, pending approvals, live schedules, unpublished changes and active incident rooms keep their history whatever its age. Working copies have their own cleanup rules.

Weekly update

Turn on Settings › Weekly report to get one update a week in a Slack channel. Choose the channel and weekly send time, and invite Ryker there first. Preview this week’s report shows what it would say before you turn it on.

The update leads with the pull requests Ryker opened and the ones already merged, then names those still waiting for review. It includes questions waiting on people, stuck work, feedback, what it learned, and model cost. When the provider reports no price, cost is labelled as an estimate at API prices; when it cannot be calculated, the report says so.

The report is built from the recorded work without another model call. Turning it on starts at the next send time. Send to the channel sends a clearly labelled preview immediately, even while the weekly report is off.

Webhooks

Webhook sources are set up under Integrations › Webhooks; there is no configuration file. Each source has its own address, /v1/hooks/<name>, a signing credential, and the conversation and environment its work goes to. The payload can never choose any of those.

  • Shapes. Any authenticated JSON, Grafana alerts, or a custom mapping of dotted paths. There is no jq, CEL, template or script of any kind.
  • Authentication. A bearer token, or an HMAC-SHA256 signature over a timestamp and the request. There is no unauthenticated option, and bodies are capped at 1 MiB.
  • Receipts. 202 means the whole batch is safely queued, not that the work is done. An exact retry returns the original receipt; the same event ID with different content returns 409. A Grafana request of up to 500 alerts is recorded all or nothing.
  • Check a payload. Paste one delivery and see exactly what it would record, without saving or sending anything.

The exact headers and the signing recipe are in the repository’s webhook reference.

Workers

Ryker runs its work on a co:op worker, which fetches the permitted repositories and runs the model and its tools in separate working copies. The bundled worker is set up for you, so most installations never change anything here.

It is a separate container. It reaches Ryker only through an outbound connection over mutual TLS, and the boxes it runs work in live in its private Docker daemon, never on the host’s Docker socket. co:op never receives Ryker’s Slack, webhook or Emisar credentials, or the GitHub App’s private key; a worker gets short-lived tokens for one repository, read-only to fetch its code and, for a publication someone approved, able to push the branch and open the pull request. A deploy never rebuilds or restarts the worker or its daemon.

When requests wait because no worker can take them, start at Settings › Advanced, then check Work › Working copies, where a full worker stops taking new work.

Releases

Install and upgrade from the repository’s main branch. A tagged release, when available for the current code, includes a Linux amd64 archive, checksums.txt and checksums.txt.bundle. Check the release notes before choosing a version.

To verify a release, place its three files in one directory. Replace the directory, version and archive name below with the files you downloaded. The first command requires cosign; the second uses the GitHub CLI.

scripts/check-release.sh DIRECTORY vX.Y.Z
gh attestation verify DIRECTORY/ryker_X.Y.Z_elixir_linux_amd64.tar.gz --repo AndrewDryga/ryker

The release check authenticates the checksum file’s signature before checking the archive. Attestation verification checks the archive’s recorded build provenance. A published release is installed by an operator; publishing it alone does not change a running installation.

How Ryker is tested

Repository checks cover formatting, compilation, lint, database behavior and deterministic tests without calling a model. Model evaluations separately exercise recorded scenarios with real model sessions. Live acceptance checks the configured integrations, while manual journeys verify the visible result against the request’s timeline.

After an upgrade, check the running version and send a real request through the integration your team uses. The testing guide documents make dev-check, make check, model evaluation and live acceptance.
