Operating it

Ryker is meant to be boring to operate: one Compose project, one helper script, one database. This page covers the parts you will actually touch.

The project

The Compose project ryker runs four services: PostgreSQL (database), the Ryker service (ryker), the bundled Coop worker (ryker-coop), and that worker’s private Docker daemon (ryker-coop-docker). Their data lives in named volumes. .ryker/compose.env, readable only by you, holds the pinned version and image and the keys generated at install.

PostgreSQL is the durable record of everything in flight: requests, work, replies waiting to be delivered, follow-ups, schedules, approvals, pull requests being published, worker placement and retention. Restarting containers resumes that work. There is no second copy of deployment state to keep in step.

Day to day

shell

scripts/compose.sh status
scripts/compose.sh logs
scripts/compose.sh stop
scripts/compose.sh start
scripts/compose.sh restart
scripts/compose.sh model-login

Every command uses the same project and the same environment file. stop keeps everything. uninstall removes the containers and network and keeps the volumes, the data and the keys. model-login signs the worker in to its model account again, Codex by default, and restarts only the worker.

Upgrade

Upgrades build from your checkout; no Ryker container image is published. Move the checkout to the release you intend to run (for example git checkout vX.Y.Z), set RYKER_VERSION in .ryker/compose.env to that version and RYKER_IMAGE to the local tag to build (for example ryker:X.Y.Z), then:

shell

scripts/compose.sh backup
scripts/compose.sh upgrade

Upgrade pulls the pinned third-party images, rebuilds the Ryker and bundled-worker images from the checkout, starts the replacements, runs database migrations as the container starts, and checks health, readiness and the exact running version. Workers enrolled on other machines are not restarted or changed.

Deploy a commit

From a checkout, scripts/deploy.sh puts the current commit into production:

shell

scripts/deploy.sh
  • It refuses a dirty tree, and a commit that is not main’s unless you pass --allow-not-main on purpose.
  • It backs the database up into .ryker/backups/ before anything changes.
  • It builds the image from a clean copy of the commit, so nothing git does not know about reaches it.
  • It replaces only the ryker container. PostgreSQL, the bundled worker and its Docker daemon keep running.
  • Only once health, readiness and the exact version check out does it pin the new version in .ryker/compose.env.

If the new version fails, the script prints the container’s last log lines and leaves the previous version pinned, so scripts/compose.sh start returns to it. Restore the pre-deploy backup first if the new version had already migrated the database.

Backup and restore

shell

scripts/compose.sh backup
scripts/compose.sh restore .ryker/backups/ryker-YYYYMMDDTHHMMSSZ.tar.gz

A backup is one archive under .ryker/backups/, readable only by you: a PostgreSQL dump, the worker’s state, and the generated environment needed to decrypt the stored credentials. It is as sensitive as the database it restores.

Restore refuses an archive whose keys differ from an existing installation. With no installation present, it restores the archived keys first, then the database, then starts Ryker and checks the exact version. A missing, wrong or damaged key must fail: never generate a new key for an existing database.

Destroy

Stopping Ryker is recoverable. Deleting its volumes and keys is not, so it takes an explicit phrase:

shell

RYKER_DESTROY_CONFIRM=delete-ryker-data scripts/compose.sh destroy

This removes the Compose volumes and the generated environment. Without a backup, the stored credentials and history cannot be recovered.

Exposure

Every port Ryker publishes binds to 127.0.0.1 by default, and Slack needs no inbound connection at all:

PortWhatPublish it?
4321Control plane, /healthz, /readyz, /metricsNever
4319GitHub App webhooks, /v1/githubOnly that path, through HTTPS
4320Signed webhooks, /v1/hooks/<source>Only that path, through HTTPS

When GitHub or another sender has to reach Ryker, put a maintained HTTPS reverse proxy in front of those two paths and nothing else; deploy/nginx/ryker.conf is an example that does exactly that and answers everything else with 404. PostgreSQL and the worker’s connection are not published at all; keep it that way.

Health and recovery

EndpointMeaning
/healthzThe process can use PostgreSQL.
/readyzIts runtimes are alive and due work is making progress. The x-ryker-version header names the running version.
/metricsQueue, delivery, worker placement and retention measurements.

When readiness fails, check scripts/compose.sh status, then scripts/compose.sh logs. In the control plane, open the stopped request and the Failures page: they say what stopped and whether a retry should work. Do not edit database rows by hand; the retry controls keep the checks that make a retry safe.

What survives a restart

PostgreSQL holds the inputs, the work, the replies waiting to be delivered, follow-ups, schedules, approvals, memory and history, so a restart picks pending work back up where it stopped. Waiting on an Emisar approval, a merge or a set time holds no model and no worker.

Credentials are stored encrypted in the same database. The keys that decrypt them are generated once at install and kept in .ryker/compose.env and in every backup.

Retention

Older data is deleted on its own. The limits are set under Settings › Data retention, and the defaults are:

Kind of dataKept for
Prompts, replies and tool activity30 days
Finished work30 days
Request history30 days
Audit trail30 days
Conversation memory90 days

The order is enforced: prompts, replies and tool activity cannot be kept longer than finished work, finished work not longer than request history, and that not longer than the audit trail. Shortening a limit deletes older data, so the page asks first.

Nothing still in use is cleaned up underneath you. Open follow-ups, blocked work, pending approvals, live schedules, unpublished changes and active incident rooms keep their history whatever its age. Working copies have their own cleanup rules.

Webhooks

Webhook sources are set up under Integrations › Webhooks; there is no configuration file. Each source has its own address, /v1/hooks/<name>, a signing credential, and the conversation and environment its work goes to. The payload can never choose any of those.

  • Shapes. Any authenticated JSON, Grafana alerts, or a custom mapping of dotted paths. There is no jq, CEL, template or script of any kind.
  • Authentication. A bearer token, or an HMAC-SHA256 signature over a timestamp and the request. There is no unauthenticated option, and bodies are capped at 40,000 bytes.
  • Receipts. 202 means the whole batch is safely queued, not that the work is done. An exact retry returns the original receipt; the same event ID with different content returns 409. A Grafana request of up to 500 alerts is recorded all or nothing.
  • Check a payload. Paste one delivery and see exactly what it would record, without saving or sending anything.

The exact headers and the signing recipe are in the repository’s webhook reference.

Workers

Ryker runs its work on a Coop worker: a machine with your code checked out that runs the model and its tools. The bundled worker is set up for you, so most installations never change anything here.

It is a separate container. It reaches Ryker only through an outbound connection over mutual TLS, and the boxes it runs work in live in its private Docker daemon, never on the host’s Docker socket. Coop never receives Ryker’s Slack, webhook, GitHub or Emisar credentials. A deploy never rebuilds or restarts the worker or its daemon.

When requests wait because no worker can take them, start at Settings › Advanced, then check Work › Working copies, where a full worker stops taking new work.

Releases

Releases are tag-driven GitHub Releases: the Linux amd64 release archive, checksums.txt, and the signature bundle for that checksum file. GitHub records build provenance separately. There is no automatic production deployment; a published release waits for an operator to install it.

Verify before you use one. Put the three files in one directory and run scripts/check-release.sh DIRECTORY vX.Y.Z: it checks the checksum file’s signature with cosign before it trusts any checksum, then the archive. gh attestation verify --repo AndrewDryga/ryker checks the build provenance.

How Ryker is tested

There are four kinds of evidence, and no single command proves all of them:

Deterministic gates
make dev-check runs formatting, compiler warnings, lint, migrations, the whole test suite in a fresh database, the control plane’s JavaScript tests and a shell-script linter. Nothing in it calls a model, and it gates every commit and every deploy. make check adds replays in an isolated database, the scripts’ self-tests and a simulated thirty days of retention; CI runs it on every push.
Model evaluation
make eval-world runs real model sessions against checked-in scenarios, the candidate against a baseline, three times each. It refuses to run with any policy that matches a production one.
Live acceptance
Runs inside the deployed ryker container, against the installation’s own settings, and posts only to a joined channel named #test or ending in -test.
Manual qualification
User-facing journeys through Chat, Slack, GitHub, webhooks, follow-ups and recovery. Each is complete only when the visible effect and the request’s timeline agree.

Fixtures are harvested, never invented

Almost every defect in a system like this is the program mishandling a well-formed model answer, and the exact answer that broke production is already on disk. So a fix comes with a deterministic test that replays that recorded answer, with no model and no credentials. A model giving an unusable answer is a prompt problem, and only model evaluation catches it.

A green gate is not a deploy, and a deploy is not proof that a live integration works. Keep those claims apart.
