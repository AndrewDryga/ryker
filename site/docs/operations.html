Running it

Responder is meant to be boring to operate: one process, one file, one lock. This page covers the parts you will actually touch — restarts, backups, retention, and the two mechanisms that tell you when something is wrong.

Deploys and restarts

Responder parks between turns. A restart converts interrupted leases back into their correct recoverable states, rehydrates approval monitors from the database, and resumes the same agent conversations. Scheduler leases carry random owner tokens, so an expired lease can be reclaimed while the process is running and the stale owner can no longer complete or retry the work that replaced it.

Waiting costs nothing. An episode waiting on an Emisar approval occupies no Slack conversation lane and no model turn.

Stop it before a migrating upgrade

Startup holds the process lock, creates and verifies a pre-migration snapshot, and only then migrates. Two processes racing that would be bad, so a second one exits instead of competing — but stop the running service first anyway.

With the split systemd units, responder.service requires the Coop unit and starts it first. Only the Coop unit holds the docker group; the Responder process never does. The unit runs doctor as a pre-start check, so a broken configuration fails to start rather than starting and failing quietly.

For self-deployment there is a three-step chain: build and prove the exact commit, roll one deployment as a canary, then promote the rest — and the promotion only proceeds after confirming the canary is still running the binary it was given. A proof is content-bound; it can never be reused for a different commit or a different binary.

Release archives are verified cosign first: authenticate the checksum manifest against its signature bundle, then check the sums, then verify build provenance. Comparing checksums against an unauthenticated manifest proves nothing at all.

State is one file — back it up

Everything durable lives in one owner-private SQLite database in your state directory: Slack inputs, webhook events, deliveries, agent runs, episodes and their event streams, evidence, coverage, memory, approvals, timelines, evaluation decisions, audit records, and the scheduler’s work index.

It runs in WAL mode with full synchronous writes, foreign keys on, and exactly one writer connection. One process owns a state directory at a time, enforced by a lock file.

Before any schema upgrade, Responder writes a verified snapshot into backups/, checks it, and confirms it still carries the source schema version — aborting before migrating if any step fails. It keeps the three newest of its own snapshots. The cleanup glob is deliberately narrow, so a snapshot you took by hand is never collected by it. That also means hand-taken copies are yours to prune.

For a point-in-time backup: stop Responder, copy the database to a directory Responder does not own — explicitly not backups/ — and restart. Coop’s state and its forks are separate. Never restore one side without the other, and run doctor, status, and failures after any recovery.

Retention

Bounded retention removes expired payloads on short horizons and keeps the record on long ones. The defaults:

SettingDefaultWhat it bounds
operational_data24hCompleted Slack inputs, webhook payloads, deliveries, and the assembled prompt context inside finished runs
closed_work7dClosed incidents and their evidence and coverage
episode_history30dThe episode record: events, attempts, context manifests, claim assessments, goals
audit_data30dAudit facts for denied and privileged actions
conversation_memory90dCompact channel and thread summaries, and their rollups
closed_session_grace15mHow long a closed Coop session waits before cleanup considers it

The ordering is validated, not merely documented: each class must be at least as long as the one before it, so operational data cannot outlive closed work, which cannot outlive episode history, which cannot outlive audit. Audit can be configured out to five years. Episode history caps at one, and it exists on that horizon deliberately: a correction queued on day thirteen has to be reviewed against an episode that still exists.

Some things are simply not deleted, and shortening a horizon does not relax it. No horizon removes an episode that a pending or approved correction, open feedback, a live wakeup, a non-terminal child, an unfinished run, or an open incident still depends on. On the operational horizon, a run a wakeup could still resume from, one the control plane could still retry, or one whose answer somebody reacted positively to is also protected — a praised reply is only an example of good behavior while the question that produced it is still beside it.

Maintenance checkpoints the write-ahead log and optimizes the database after pruning.

Webhooks and dedup

Routes accept POSTs of JSON under a size cap, on loopback, published through your proxy. Two auth modes: a bearer token, or an HMAC signature over the timestamp, the event ID, and the raw body within a five-minute window. Every secret is at least 16 bytes.

Delivery identity is the X-Responder-Event-ID header when you send one, and a digest of the body when you do not. The body digest is stored either way. Reusing an event ID with different content returns 409 rather than silently accepting one of the two.

That identity is derived before normalization on purpose. It is the identity the signature binds, and a change route takes its ledger identity from it — so a redelivery records one change, and a replay under a new event ID fails the signature.

Grafana routes read fingerprints and group keys natively. Generic routes use small dot-path mappings, with no jq, CEL, templates, or scripting of any kind. A change route’s kind must be inside the closed vocabulary; a value outside it is rejected with a 400 rather than quietly recorded as a deploy, because a mapping typo should stop where you can see it.

Socket Mode does not replay events from while you were offline, so there is a bounded startup catch-up window — 15 minutes by default, up to 24 hours, and zero to disable. It re-reads app notifications only. Human conversation is never replayed by catch-up.

Repository mirrors

Declare a repository by slug and Responder owns the clone. It lives under your state directory, keyed by owner and name, and there is exactly one place in the product that constructs that path.

The maintenance lane fetches and fast-forwards every managed clone on an interval that defaults to fifteen minutes. It never modifies the work tree. A turn whose clone has lapsed pays for a bounded fetch before its session forks.

A fetch that fails degrades to recorded staleness rather than blocking a turn: every context manifest records the revision and when it was last fetched, so “how old was the code the model read” has an answer. Failures show up in doctor and as a gauge on /metrics, named to say what it means — the clones whose evidence is stale, not whose work is stalled.

Routing profiles

A Coop session policy names one target, or an ordered ladder of up to four that may cross providers. When a session is rate-limited, Coop rotates to the next rung that is not cooling and re-delivers the same turn itself, so Responder sees an ordinary completion on a different model. A rate limit is not a failure and never spends an attempt.

Crossing providers drops the model’s own in-session history. That costs its prior reasoning and nothing the run depends on, because Responder restates durable context in every prompt. Only when every rung is cooling does the turn fail as rate-limited, and it then waits on the reported reset instant, re-checking at least every half hour.

Four execution profiles let one repository route its lanes at different policies:

chat
Conversation and small focused checks addressed to Responder.
investigate
Deep read-only operational work with tools.
engineer
Writable repository work in an isolated fork.
watch
The attention decision on a message nobody addressed to Responder.

Responder decides which profile a turn asks for before any model runs, and records it on the manifest beside the model that actually answered. A profile names a policy and nothing else — the ladder, the reasoning effort and the budget stay in the owner-private policy file, and a profile can never widen authority. Omitting the block entirely behaves exactly like a deployment from before profiles existed. Move one lane at a time and check the split on the Usage page before moving the next.

There is deliberately no Slack command that changes a provider account or a model policy.

The eval idea

The rule underneath all of this: no test in the fast gate may call a model.

Almost every defect in a system like this is the host mishandling a well-formed answer — suppression rebuilding a reply it had just cleared, a conflict response read as “this work is finished”, a whole result discarded because a confidence field held a number instead of a word. None of those need a model to reproduce. They need the exact answer that broke production, and that answer is already on disk.

So there are two kinds of check, and knowing which one you need is the diagnosis:

The host mishandled a valid answer
An ordinary Go test beside the code, plus a recorded fixture. Deterministic, offline, no credentials, about a second. This runs on every commit.
The model produced an unusable answer
A prompt problem, and no amount of host testing fixes it. That needs the real-model evaluation, and it is run when prompts, contracts, or operation schemas change.

The offline replay is the day-to-day gate: recorded real answers pushed through the strict production parsers, so a prompt, model or schema change fails the build when it breaks an accepted contract. A broader deterministic gate adds the customer journeys with fake Slack, Coop, Emisar and GitHub boundaries — it uses no credentials, calls no model, creates no channels, and touches no infrastructure.

The real-model evaluation is the other half. Each case runs through its own isolated Coop session using the production prompts and tool configuration, and the workspace is discarded only after Coop proves it is clean — a dirty workspace fails the case and keeps the session. Results are recorded, so a release can say whether answers are improving, not merely that a gate passed.

Two things about that corpus are worth copying if you build something similar. Cases are compared by name: a case the baseline does not know is not a regression, but a case the baseline knows that has gone missing is a failure — deleting a fixture must not be a way to make its regression disappear. And there are two separate regression knobs, a pass rate and a judge score, because a judge’s five-point scale is not a rate and one knob for both would be useless for one of them.

Fixtures are harvested, never invented

Hundreds of real model answers are already recorded, alongside the prompts that produced them. The exact result that broke production is on disk. A fix without the test that would have caught it is a fix with a scheduled return date.

The watchdog

Some failures no test catches, because the machine simply stopped. On one occasion the Docker daemon died, Coop’s control API kept answering, /readyz kept reporting ready, every turn died inside execution, and the operator found out by noticing that Slack had gone quiet.

So the watchdog’s primary signal is not a health endpoint. It is whether due work has moved. A queue that is not draining is the one symptom every outage shares. It checks readiness too, because that catches a disconnected socket on an idle afternoon.

It reads each deployment’s database read-only and immutable — a watchdog that trips on its own lock is worse than none — and reports an unreadable database as unreadable, never as zero. It alarms after a sustained stall across several consecutive checks, so a few seconds of unreadiness during a deploy passes silently.

Two details earn their place. It distinguishes provider-limited — every stalled run parked on a rate-limit retry — from unexplained, because “waiting on rate limits” and “wedged” look identical otherwise. And it alarms through a desktop notification, a log file, and a Slack DM to the deployment’s first configured operator, added after a queue sat wedged for eleven hours behind a notification nobody saw. The bot token is the right transport for that, because the Slack app outlives the process using it.

Recovery has to show real movement. A momentarily empty queue is not an all-clear; a backoff phase once produced a cheerful “queue is moving again” on a stall that then ran another two hours. And it writes a heartbeat first thing on every run, because this script is silent when everything is well and also silent when it is dead.

It is exercised by the fast gate on every change, deliberately: the only way to know it still fires is to break something on purpose every time the tree moves.

Day to day

shell

# counters, and the bounded incident directory
responder status --config /etc/responder/responder.yaml --json

# what failed, and whether it can be retried
responder failures --config /etc/responder/responder.yaml

# put exactly one item back on the queue
responder retry --config /etc/responder/responder.yaml \
  delivery delivery_9b2e4c71

# re-run a saved Slack message, privately
responder replay slack --url <slack-permalink>

# the process can use its database
curl -f http://127.0.0.1:8080/healthz
# …and Slack, Coop, and every lane are alive
curl -f http://127.0.0.1:8080/readyz
curl -f http://127.0.0.1:8080/metrics

status and failures open the current schema without migrating it and need neither Slack nor Coop, so they work when the service does not.

retry takes exactly one item, preserves its original payload, frozen revision and idempotency key, resets the failure budget, and appends an audit event. It refuses to run while Responder owns the state directory. There is deliberately no bulk retry.

replay slack is the post-fix verification tool. It clones the saved text, attachments, actor, channel, thread and timestamp behind a permalink, gives the clone a fresh identity, and queues it through the running service. Replays are private by default: the real model and tool path runs, but Slack status, reactions, messages, offers, schedules, tasks and incidents are all suppressed. Add --publish only when another real response in that conversation is intentional. If the command hits its timeout it cancels the durable run and interrupts the exact Coop turn — and if it cannot confirm that immediately, it says so rather than reporting a clean stop.

Capacity and limits

The knobs you are most likely to touch:

Incidents
One limit bounds concurrently active incidents (and therefore open Coop sessions); another bounds all non-closed incidents and is enforced transactionally before a channel is created. Set the second above the first.
Member tasks
Per-member open-task caps, a creation cooldown, and a reserved pool of slots so contributor work cannot crowd out incidents and operator work.
Turn ceiling
A lifetime safety ceiling measured in accepted requests, not tool calls, defaulting to 1000. Responder allocates capacity automatically as authorized requests arrive; operators never estimate how many turns an investigation needs. At the ceiling the pending request, session and fork are preserved and deferred, not failed.
Retry budgets
Four independent ones — webhooks, Slack inputs, deliveries, agent runs. Scheduling deferrals and progress polls do not consume them.
Worker lanes
Control, background, and maintenance, sized separately. Slack controls stay on the control lane while long turns stay on background, so an approval or a stop is never blocked behind an investigation.

Secrets are read at startup and rotated by restart. The Emisar key needs a little more care: park the work, stop Coop and Responder, update the environment, rerun bootstrap-coop, restart. bootstrap-coop refuses to rewrite configuration while the Coop socket is still accepting connections, and it never prints the key.
