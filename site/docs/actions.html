Approvals and automation

Ask Ryker to prepare a code change, carry out an infrastructure action, or check something later. Here is how you review the work, approve what needs a decision, and manage recurring requests.

Connect running systems through Emisar

Connect an Emisar account to an environment to let Ryker access running systems. Emisar exposes defined actions and decides which may run, which need approval and which are denied. It also executes and records them. Ryker can request an action but cannot approve it. Without an account, Ryker can explain an infrastructure change for you to carry out.

The API key acts as a person or service account whose runner access determines which systems Ryker can reach. For enforced read-only investigations, allowlist the required read actions and restrict the runner’s host permissions. For fixes, enable the needed actions with an appropriate approval policy. The key has no separate read-only setting. How Emisar limits access.

Approvals

When an action needs approval, Ryker posts an Emisar review card in the same conversation, naming the exact action and where it would run, with a Open approval button. Open it to review the request in Emisar, where an authorized person makes the decision. The action waits for that decision.

The approval link opens the exact request on your configured Emisar address. Ryker checks the link before showing it.

Ryker updates the card as the run progresses. The wait survives a restart and uses no model time. When the run finishes, Ryker continues the conversation.

Check the result

After the action runs, Ryker checks its intended effect with fresh read-only evidence where available. The approval and the observed result are recorded separately.

An approved Emisar action can change running infrastructure. Deploying code from a pull request stays in your team’s release process.

Code changes and draft pull requests

A code task works in a separate checkout inside co:op. When the change is ready, it goes through review before becoming a draft pull request:

  1. The co:op worker compares the change with the current repository, rebases it and runs the configured checks.
  2. Ryker records the reviewed commit and tree. Publication uses that exact reviewed change.
  3. The worker pushes a Ryker-owned branch and creates or updates a draft pull request. A branch changed outside Ryker is not overwritten.
  4. Your team reviews the draft, marks it ready and merges it.

The GitHub App’s private key stays with Ryker. The trusted worker receives a short-lived token scoped to the repository for an authorized publication; that credential stays outside the model’s sandbox.

A failing configured check, rebase conflict or policy finding blocks publication. A check that could not start, did not run, or is not configured is named on the draft as missing, so the pull request never reads as more verified than it is.

Who publishes: opening pull requests is off until you turn it on in the GitHub integration. Once it is on, a confirmed task whose confirmer named the repository opens its own draft when the review is clean; otherwise a configured operator presses Create draft PR.

After the pull request

GitHub tells Ryker when checks finish and when the pull request is merged or closed, and Ryker posts each change once in the task’s thread. Ryker also checks an open pull request itself every 10 minutes, so it keeps up when GitHub cannot reach it. If checks fail on the published commit, the task picks the work back up, corrects it within its scope, and updates the same pull request. Review comments on the pull request go back to the same task.

For 30 days after publication, a deployment or Terraform message in another watched channel is linked back to the task only when it names the exact pull request, branch or commit. A match by topic, repository name or timing is ignored.

Reviews on GitHub

Ask Ryker to review a pull request in Slack, GitHub or Chat. With the repository connected, it can read the diff and discussion, leave comments on specific lines, and submit a review requesting changes. Replies in a review thread stay in that thread. On GitHub, people need write or admin access to the repository to request work.

A review is tied to the exact commit it examined. Approving a pull request is a separate repository setting, off until you enable it. Your team decides what to merge; Ryker has no merge operation.

For feedback and failed checks on Ryker’s own pull requests, see how it follows through after publication.

Follow-ups

A follow-up continues an existing request after a wait: “check again in two minutes,” “come back when this merges,” or “ask me after the rollout.”

Ryker can continue the request at a set time, after an event, or when someone answers. An event wait can stay open without a deadline. If you set a deadline, Ryker can also check back sooner. The wait survives restarts and uses no model or worker. An unrelated event cannot wake it.

Ryker can add a follow-up while working, or you can request one. Find these under Automations › Follow-ups; close the original request to stop its follow-up. For a new check at a set time or a recurring routine, use a confirmed schedule below.

Schedules

Ask in ordinary language, in the place where the results should go: “every weekday at 09:00 check production health”, or “on the first of each month prepare an SRE review”. Ryker answers with a card showing the schedule it would save, and nothing runs until it is confirmed: in Slack by a configured operator, and on GitHub by someone with write access to the repository.

A schedule runs once, on an interval from five minutes to a year, or daily, weekly or monthly, in the timezone you name, and it can carry an end date. Two runs of the same schedule never overlap. A run that cannot start within 15 minutes of its time is recorded as missed, and the next one still starts on time.

Each scheduled run gets fresh context and follows the same environment and Emisar policy as a message from a person. Its page says what its runs may do: only look, change the repository, or carry out operations a person approves in Emisar. Run now, Pause, Resume and Delete are under Automations › Schedules and in App Home; to change what a schedule does, ask Ryker where it was set up.

Standing requests and rules

A standing request is saved under Automations › Rules. It tells Ryker to act when something happens: a Terraform plan posted in a channel, a deployment, an alert, or a GitHub, Slack or webhook event that matches an exact filter. Say it in words, “when someone posts a Terraform plan here, review it for risky changes”, and Ryker shows the rule it would save: what it listens for, where it reads and replies, what it does, and when it ends. Nothing is saved until an operator confirms.

Each rule has a structured event filter. Ryker matches events against that saved filter in code. A matching event starts an assessment. Ryker may ignore a duplicate or interim update, react, reply, or start work. Manage rules under Automations › Rules, in App Home, or with /ryker assignments.

Cleanup

Cleanup goes by ownership, never by name. Ryker records the exact worker session behind each task. When the work finishes, it closes that session, waits fifteen minutes, and asks the worker for an exact plan before removing anything:

  • A clean working copy with nothing unreviewed is removed.
  • Committed work is removed only once it is safe in a draft pull request, or when an operator chooses Discard unmerged.
  • Uncommitted changes are never discarded. Not automatically, not from Slack, not from the console.
  • Deleting a Slack room does not discard the work behind it.
  • Working copies Ryker did not record are outside its cleanup entirely.

Working copies, and the space each worker has left, are under Work › Working copies.

Your controls

  • Your team releases code. Ryker opens drafts on its own branches; people mark them ready, merge, sign and deploy.
  • Emisar controls infrastructure changes. Its policy decides what can run and who approves it. Ryker cannot approve a request itself.
  • You choose the scope. Read-only repositories stay read-only. A message, reaction or event cannot expand access or approve an action.
  • You choose what is saved. Rules, schedules, facts and preferences need an instruction or confirmation. An operator’s explicit correction can become guidance without a second confirmation.
  • Uncommitted work is retained. Closing a task or running cleanup does not discard it.
