Governed action

Ryker has no production shell. Everything it can change runs through a gate it does not own: Emisar for running systems, and a draft pull request for code. This page is those gates, end to end.

Emisar, in one paragraph

Emisar is the infrastructure authority. It publishes typed actions, decides by policy what may run, what must wait for a person and what is denied, and it owns approval, execution and audit. Ryker is a client of that system. It can find an action and ask for it to run; it cannot approve one, and it holds no infrastructure access beyond the Emisar account an environment is given. An environment with no account can only be told what to run.

Scope the account

Where Ryker should only investigate, give it an observe-only Emisar credential. To let it carry out fixes, use a narrowly scoped one. Emisar’s own policy, approvals and audit stay in charge either way; nothing written in a prompt grants authority.

Approvals

When an action needs approval, Ryker posts an Emisar review card in the same conversation, naming the exact action and where it would run, with a Review in Emisar button. Opening it is navigation, not approval. Nothing has run yet, and the decision is made in Emisar, by a person, under Emisar’s policy and audit.

Ryker checks the approval link before it shows it: it must be HTTPS, on your configured Emisar address, and point at that exact approval request with nothing added. Anything else is dropped rather than rendered.

Then Ryker watches that exact run in the background and updates the card as it moves. Waiting uses no model time and survives a restart. When the run finishes, the same conversation continues.

Approval is not success

This is the part most systems get wrong. An approval is permission to run, never proof that the change worked. After the run, Ryker checks the intended effect with read-only evidence where it can.

One precise nuance

“Cannot deploy” means Ryker cannot deploy from repository changes. An approved Emisar action can change running infrastructure; that is what the approval is for.

Code changes and draft pull requests

Engineering work ends as a draft pull request from an isolated working copy, and a person merges it. Publication is where Ryker is most careful, because it is the one place it writes to something you keep.

  1. The worker returns the complete reviewed patch, the exact parent commit, and the tree it approved.
  2. Ryker makes a throwaway checkout of that parent and applies the patch.
  3. If the resulting tree does not match the approved tree exactly, nothing is published.
  4. It pushes a Ryker-owned branch, leased against the commit it last recorded, so a branch that changed outside Ryker is never overwritten.
  5. It creates or updates a draft pull request, never a ready one.

The GitHub credential never enters the model’s box. It reaches git only for the one command that needs it, never in a remote URL or a file on disk.

Your repository’s own checks are evidence, and they count. A check that ran and failed blocks the draft, and so do rebase conflicts and policy findings. A check that could not start, did not run, or is not configured is named on the draft as missing, so the pull request never reads as more verified than it is.

Who publishes: opening pull requests is off until you turn it on in the GitHub integration. Once it is on, a confirmed task whose confirmer named the repository opens its own draft when the review is clean; otherwise a configured operator presses Create draft PR.

After the pull request

GitHub tells Ryker when checks finish and when the pull request is merged or closed, and Ryker posts each change once in the task’s thread. Ryker also checks an open pull request itself every 10 minutes, so it keeps up when GitHub cannot reach it. Check delivery asks GitHub again right away. If checks fail on the published commit, the task picks the work back up, corrects it within its scope, and updates the same pull request. Review comments on the pull request go back to the same task.

For 30 days after publication, a deployment or Terraform message in another watched channel is linked back to the task only when it names the exact pull request, branch or commit. A match by topic, repository name or timing is ignored.

Follow-ups

Work often has to stop and wait for something else. Ryker makes that a paused request, not a polling loop.

A follow-up waits for a set time, for something to happen (a pull request merged, a deployment finished), or for a person’s answer, and then picks the same request back up. One that waits for an event can have no timer at all; one with a deadline can also check back earlier. While it waits it holds no model and no worker, it survives restarts, and only the exact event it waits for wakes it.

Ryker adds follow-ups on its own when work has to wait, and you can ask for one: “check again tomorrow morning.” They are listed under Automations › Follow-ups. To stop one, close the request it continues.

Schedules

Ask in ordinary language, in the place where the results should go: “every weekday at 09:00 check production health”, or “on the first of each month prepare an SRE review”. Ryker answers with a card showing the schedule it would save, and nothing runs until it is confirmed: in Slack by a configured operator, and on GitHub by someone with write access to the repository.

A schedule runs once, on an interval from five minutes to a year, or daily, weekly or monthly, in the timezone you name, and it can carry an end date. Two runs of the same schedule never overlap. A run that cannot start within 15 minutes of its time is recorded as missed, and the next one still starts on time.

A schedule is a wake-up, not stored permission. Each run is an ordinary request with fresh context: the same pipeline, environment and Emisar policy as a message from a person. Its page says what its runs may do: only look, change the repository, or carry out operations a person approves in Emisar. Run now, Pause, Resume and Delete are under Automations › Schedules and in App Home; to change what a schedule does, ask Ryker where it was set up.

Rules

A rule tells Ryker to act when something happens: a Terraform plan posted in a channel, a deployment, an alert, or a GitHub, Slack or webhook event that matches an exact filter. Say it in words, “when someone posts a Terraform plan here, review it for risky changes”, and Ryker shows the rule it would save: what it listens for, where it reads and replies, what it does, and when it ends. Nothing is saved until an operator confirms.

Matching is exact and done by Ryker, not by the model, and prose never becomes a trigger. A match asks Ryker to look at the event, not to speak: it may ignore a duplicate or an in-between update, react, reply, or start work. Rules are paused, resumed or deleted under Automations › Rules, in App Home, or with /ryker assignments.

Cleanup

Cleanup goes by ownership, never by name. Ryker records the exact worker session behind each task. When the work finishes, it closes that session, waits fifteen minutes, and asks the worker for an exact plan before removing anything:

  • A clean working copy with nothing unreviewed is removed.
  • Committed work is removed only once it is safe in a draft pull request, or when an operator chooses Discard unmerged.
  • Uncommitted changes are never discarded. Not automatically, not from Slack, not from the control plane.
  • Deleting a Slack room does not discard the work behind it.
  • Working copies Ryker did not record are outside its cleanup entirely.

Working copies, and the space each worker has left, are under Work › Working copies.

What it cannot do

  • Merge, deploy from repository changes, or sign a commit. No operation for these exists.
  • Approve an action, or run one outside Emisar. Approval is a person’s decision in Emisar.
  • Open anything but a draft pull request, or push to a branch it does not own.
  • Change a read-only repository of its environment.
  • Turn a reaction or a payload into authority. Neither can approve anything, or choose where work runs and what it may change.
  • Save a rule, schedule, fact or preference on its own. It proposes one, and a person confirms it.
  • Discard uncommitted work. Not the cleanup, not Slack, not the control plane.
