Governed action

Responder has no production shell. Everything it can change runs through a gate it does not own. This page is that gate, end to end: how an action is found, who approves it, what it can earn, and where the boundary is drawn every time.

Emisar, in one paragraph

Emisar is the infrastructure authority. It publishes a catalog of typed actions in signed packs, decides by policy what may run, what must wait for a person, and what is denied, and it owns approval, execution and audit. As the Slack app description puts it, an outbound-only runner validates the action, its arguments, its limits, and the trusted pack hash again on the target host before execution. Responder is a client of that system. It can discover an action and submit one; it cannot approve one, and it holds no infrastructure credential of its own.

The shape of the boundary

Model-proposed, inferred, and autonomous operational mutation is disabled. A configured operator may directly request one exact action in any Slack conversation. An incident room is coordination context — it is not an authorization boundary, and it is not required.

Typed actions and discovery

An action has an immutable identity of three parts: the action, the pack it came from, and the runner that would execute it. All three are required, and they are compared as opaque identifiers — trimmed, never case-folded, because Emisar assigned them. A pack reference carries both a version and a digest, so nomad@1.4.0+sha256:… names one exact pack and no other.

Discovery is a real contract, not a convention. At startup Responder initializes the Emisar tool catalog and refuses to run if any of find_actions, get_action, list_runners or run_action is missing. It also checks the server identity and protocol version. This validates authentication and the catalog without executing anything.

The model must find the action; it may not invent one. And it may not claim a capability does not exist without first listing every pack, including the ones not currently available. “There is no action for that” is a finding that has to be earned.

Authority is stored on the work itself, in three values: read_only, repository_write, and governed_operation. Effort never grants authority. A deep health review stays read-only; a narrowly scoped governed operation can require approval without becoming an incident.

Approvals

When Emisar answers pending_approval, Responder copies the exact run, operation, pack and runner references, the approval request, its URL and its expiry — and then checks all of it before anything reaches Slack.

The envelope is accepted only when the requester is a configured operator, every identifier is present, the status is exactly pending_approval, and the expiry is set and still in the future. The URL is checked harder than that:

  • The scheme must be https, with a host, and with no userinfo, no query string, and no fragment.
  • The host must match your configured Emisar endpoint. Same origin, or it is dropped.
  • The path must begin /app/, contain /approvals/, and end with the escaped request ID it claims to be for.

Anything else yields an empty URL, and an empty URL drops the whole pending approval rather than rendering a link nobody checked.

Slack then shows exactly one control: Review approval in Emisar. There is no approve button and no reject button. They were not hidden behind a permission check — nothing in the product composes them any more. The decision is made in Emisar, by a person, under Emisar’s policy, and recorded in Emisar’s audit.

The card carries a blast-radius strip of three fields: the action, the runner, and the pack. It shows no target row and no policy row, because those were never recorded — and a blast-radius strip that guesses the blast radius is worse than one that stops at what it knows.

Responder watches that exact run in the background, updating the card as it progresses, and posts the terminal result plus read-only verification into the same conversation. Waiting consumes no model turn and survives a restart. On every poll it re-checks the immutable identity: if the run, operation, action, pack or runner has drifted, it refuses rather than following the new thing. Emisar reports fourteen distinct run statuses; Slack renders them as three answers, and denied is rendered grey rather than red — an operator declining a change is the control working, not a failure.

Approval is not success

This is the part most systems get wrong. An approval resolves the waiting episode and queues a separate verification episode. Approval is authorization to dispatch, never proof that the requested effect happened.

During verification, Responder cannot run the action again, and cannot substitute a different run. The continuation prompt forbids it outright. Verification is read-only, and it is a different episode with its own record — which is also what funds the trust ladder below.

What it cannot do

  • Merge, deploy from repository changes, or sign a commit. No operation for these exists.
  • Submit unattended. The “may submit without a person” decision is false in every branch of this build.
  • Approve, or act past an approval. Including repeating the mutation while verifying it.
  • Widen its own authority. An offer that skips a rung, or claims more successes than the host counted, is refused.
  • Push an arbitrary branch, open a non-draft pull request, or publish changes to a companion repository.
  • Archive a Slack channel.
  • Turn a reaction into authority. A reaction never authorizes an approval, a change, an incident, or an action.
  • Write memory, a preference, or a rule. It can only propose one for a person to confirm.
  • Discard dirty work. Not the janitor, not Slack, not the control plane.

One precise nuance

“Cannot deploy” means it cannot deploy from repository changes. An approved Emisar action can absolutely change running infrastructure — that is the point of the approval. The change ledger records such a run as a configuration change, deliberately not as a deploy.

Runbook drafts

When an episode ends with a verified remediation, Responder can offer to write it down as an Emisar runbook draft. Be precise about what that means: Responder creates one unpublished draft. It does not validate, publish, or execute runbooks. Emisar alone decides whether a draft is ever published.

The offer is refused unless two things are true: the episode’s outcome is recorded as verified, and the action named is one this same episode ran successfully. The step is rebuilt from the recorded action reference, not from anything the model typed — even on an exact match, the stored row is the one that is used. There is no path by which a byte a model wrote reaches Emisar.

The generated draft is deliberately incomplete. Its arguments, outputs, success conditions and waits are empty, because a step whose arguments were invented would be worse than a step a human has to fill in. If Emisar echoes back a different slug than the one requested, that is a hard refusal.

A sibling offer writes a knowledge-base card into your repository instead — an ordinary engineering task that ends as a draft pull request nobody is obliged to merge.

Grant promotions

Trust here is earned in a countable way, one rung at a time, for one exact action in one exact situation.

observe
It may look, and say what it would do.
propose
It may put the exact action in front of you.
one_click
The ceiling in this build. A latency rung, not an authority rung: Emisar still approves every run.
auto
Specified, and not implemented. A stored value is clamped down and the reason says so.

Promotion needs three verified successes — three because it is the smallest number that is not a coincidence — and every grant expires, with a default of thirty days. Authority is never granted permanently.

The count is not the model’s. The host recomputes it from its own records: Emisar approvals that succeeded, joined to the runs they caused, joined to episodes whose outcome was verified, scoped to the exact channel, alert group and repository. A claim larger than that recomputed number is refused. So is a promotion that skips a rung, or one that widens the grant it says it is extending.

Three parties, none of them skippable: the model proposes, the host recomputes, the operator confirms. The evaluated grant comes back with no granter recorded, so it cannot validate until a click supplies one. There is deliberately no decline button — ignoring the card is declining it.

Demotion is automatic, immediate, and drops exactly one rung while zeroing the count. It fires on a failed verification, an expiry, a changed target contract, or an operator saying so, and it applies to every situation holding that action. A pack upgrade or a different runner starts trust counting from zero, because it is not the same thing any more.

Standing assignments

A standing assignment is an operator delegating one narrow class of change, watched for by a signal pattern, bounded by a daily budget and an expiry date.

The change classes are a closed allowlist of five, and the set is closed because free text means Responder may change anything:

  • dependency_upgrade
  • alert_threshold
  • flaky_test_quarantine
  • observability
  • documentation

The daily budget runs from 1 to 20, defaulting to 1. The expiry runs from 1 to 90 days, defaulting to 14. Up to ten path globs may narrow it further, and a glob containing .. is refused.

Shadow only, in this build

Every standing assignment is created in shadow, and the store refuses to create one that is not. It evaluates real signals and records exactly what it would have done — and nothing opens. Clearing that flag is a separate decision with no operator surface yet. Read the shadow ledger before you ask for more.

The gate runs cheapest-check-first and is identical in shadow and live: the assignment must be live, in this channel, with every word of its signal pattern present in the message. The same issue must have recurred at least three times in a fourteen-day window. The investigation must have finished decision_ready with zero material gaps. And at least one evidence row must come from Emisar, monitoring, or GitHub — because a change justified solely by reading the repository is a change justified by what somebody intended.

Every evaluation is recorded three ways: a durable row, an audit event, and an episode event that a replay fixture can contain. Declines are recorded too, with the reason. Two store invariants do the real work: a uniqueness constraint on the assignment and the issue makes “one pull request per issue” structural rather than careful, and counting today’s rows is the budget. It claims before it acts, so a crash leaves an issue handled rather than handled twice.

Creating one is a conversation. Say what you want watched and Responder answers with a confirmation card showing the normalized bounds — repository, change class, daily budget, expiry, path globs, signal. The typed create subcommand was retired: it was a nine-key line where a miscounted path list was a repository-wide grant that read as a narrow one. The button carries only which offer; the bounds are re-read from the record at confirm time, and a card clicked in a different channel than it was issued for is refused.

Schedules

Ask in ordinary language — “every weekday at 09:00 check production health”, “on the first of each month prepare an SRE review” — and a configured operator gets a confirmation card. Nothing runs until it is confirmed.

Five recurrences: once, interval, daily, weekly, monthly. Intervals run from five minutes to a year. Times are IANA timezones, and a wall-clock time that does not exist on a spring daylight-saving transition is skipped rather than silently shifted. Nothing schedules permanently: a task expires after 7, 30, 90 or 365 days.

The card shows your request quoted back, the title, the cadence and next run in the task’s own timezone, the destination, the repository, and the boundary in plain words: each occurrence re-runs the request through current policy, it cannot reuse an old approval, and overlapping occurrences are skipped. Batch offers are all-or-none.

After downtime, catch_up decides between running the single latest missed occurrence and skipping it, bounded by a misfire grace period. The scheduler records each occurrence before dispatch, and never overlaps two copies of the same task.

The most important sentence about schedules is that they are not an execution engine. A scheduled occurrence creates an ordinary Slack input and runs the ordinary pipeline — the same conversation serialization, Coop policy, memory assembly, tool projection, Slack status, evidence contract, and approval continuation an operator message gets. A schedule is a durable wake-up, not stored authority.

External waits and wakeups

Work often has to stop and watch something else finish. Responder makes that a first-class state instead of a polling loop.

A turn can declare a wait with a kind — github_checks, deployment, terraform_run, emisar_approval, scheduled_verification, or other — an event matcher naming the exact thing to watch, and when to look again. The wakeup is durable: it has its own state, its own lease with a fencing token, and its own deadline, and it survives a restart.

While waiting, nothing is posted. The turn returns silence with a declared wait rather than a heartbeat message. When the wakeup fires it becomes one bounded re-check, carrying the frozen prior context. A wakeup may never widen the audience — it falls back to the thread that scheduled it rather than posting to the channel, because the loudest possible reading of missing information is the wrong one.

Terraform is the worked example, and the rules are enforced by the host, not suggested to the model. A run that is not yet terminal must declare a wait naming the exact run ID, with both a next-poll time and a deadline. A verdict of “needs review” must carry the canonical provider run URL and fresh evidence about the affected scope, so an operator can see whether production is safe before the change.

Draft-PR publication

Engineering work ends as a reviewed draft pull request from an isolated fork. A person merges. The publication path is where Responder is most paranoid, because it is the one place it writes to something you keep.

  1. Coop returns a complete reviewed patch, the exact parent commit, and the candidate tree it approved.
  2. Responder builds a throwaway private checkout, fetches that exact parent, and applies the patch.
  3. It runs git write-tree. If the result does not equal Coop’s candidate tree byte for byte, publication is refused and the message names both hashes.
  4. It pushes a deterministic Responder-owned branch with --force-with-lease, leased against the SHA it recorded. A branch that already exists and was not recorded is not overwritten. A branch that changed outside Responder is refused, naming expected and found.
  5. It creates or updates a draft pull request, then verifies the PR still preserves the branch at the pushed SHA.

The GitHub credential never enters the agent box. It reaches git as a per-invocation configuration header: never a URL, never an argument visible in a process table, never a credential helper file on disk. The agent reads your code with no GitHub credential inside its box at all.

Your repository gate is validation evidence, not publication authority. A missing gate, a failed gate, a gate that would not start, or a gate that modified tracked files becomes a warning on the draft PR — and gate-authored changes are discarded rather than smuggled into the diff. Rebase conflicts, a moving source branch, an incomplete reviewed patch, and policy findings all still block publication outright.

After publication, a host-owned follower polls for check, close and merge transitions and writes deduplicated updates back to the original task thread. A Slack message can contribute a deployment or Terraform event to that record only when it names an exact recorded PR number, branch, head SHA or merge SHA. The model cannot broaden that binding.

Verified discard

Cleanup is ownership-based, never name-based. Responder records the exact Coop session ID, then asks for a discard plan, and that plan pins the revision, the workspace identity, the branch, the head, a status digest, whether the tree is dirty, whether it is unmerged, and whether anything is still running.

The rules on top of that plan are short:

  • The session must be closed, with no active turn and nothing queued.
  • Dirty work is never discarded. Not automatically, not from Slack, not from the control plane.
  • Unmerged work is discarded only after its reviewed tree is durable in a draft PR — and then only when a second, explicitly acknowledged plan comes back still clean.
  • Deleting a Slack room does not discard the work behind it.
  • Forks Responder did not record are outside its cleanup set entirely.
