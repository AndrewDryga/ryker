The console

Open Ryker’s console to see how each answer came together and change how it works for your team. Inspect the recorded model setup, instructions, context and tool calls, then tune models, instructions, memory and access in one place.

Open the console

For an overview of permissions and data handling, read access and data.

Open http://127.0.0.1:4321 on the host running Ryker, or use your installation’s published address. Everyone signs in, including people on the host itself.

  • From Slack: operators send /ryker sign-in or press Open the console in Ryker’s App Home. The link works once, within 15 minutes.
  • From the host: run scripts/compose.sh sign-in for a link that works once, within an hour. The installer prints one that opens setup.
  • Invite someone: anyone signed in can create an invitation under Settings › Access. It works once, within seven days.

A browser stays signed in until 30 days after it was last used. Settings › Access lists signed-in browsers and lets you sign them out. Everyone signed in can see and change the whole installation; there are no separate roles.

For remote access, use an SSH tunnel, Cloudflare Tunnel or Tailscale Serve. Ryker handles sign-in itself; it can also recognize configured Cloudflare Access or Tailscale Serve identities. Set up network access.

The console serves its own fonts and scripts, without third-party analytics. Your requests use the model account, workers and integrations you connect. Stored integration credentials appear as configured, missing or unusable; their values are not rendered.

Pages include How this page works help. Filters stay in the address, so you can share a filtered list or link to an exact request. Actions that retry, discard, pause or delete work ask for confirmation and record the change.

A request’s timeline

Open a request from Activity to follow its four stages: Intake, Routing, Work and Answer. The top says where the request stands, how long it took, what it cost, and what it is waiting for, if anything.

Intake
The message that started it: what Ryker extracted, the input as received, and the original message.
Routing
The channel settings and rules that applied, and the decision Ryker made, with its reason. A check that never ran says “Not checked”, never “No”.
Work
The worker and working copy it ran on, the exact briefing sent to the model, including what was left out to fit, the answer that came back, each check on that answer, and every tool the model used.
Answer
What was delivered, and where.

Background learning and cleanup that followed come after the answer, at their own recorded times. Every card has a link to itself, so you can share the exact step. Earlier activity loads a page at a time, within your retention settings.

Missing records are labelled Not recorded. The timeline keeps the settings and evidence used at the time, rather than reconstructing them from today’s configuration.

If an answer misses something, start with its Work briefing. Check which instructions and memories were included, what repositories it could read, and which tools it used. Edit Instructions to change your team’s guidance, correct saved knowledge under Memory, or adjust the model and reasoning effort under Settings › Models. Return to the next request’s timeline to see what changed.

Failures

The Failures page lists work Ryker could not finish on its own, newest first. Affects people comes first: someone is still waiting for a reply, an update or a result. Housekeeping is cleanup nobody waits on.

Each row says what stopped, who it affects, why Ryker stopped trying, and whether a retry should work: Retry should work, Needs you, Fix needed first, Retry won’t help, or Retrying on its own. A row has a button only when pressing it can help, and says what the button does before you press it. When something else has to change first, such as a token or Ryker’s place in a Slack channel, the row links to where to change it.

A failure’s own page tells the whole story: what happened, what it affects, what Ryker already tried, and each thing you can do, recommended first, including what happens if nobody acts. Ryker retries most things several times before it lists them, and an item leaves the list once its work finishes.

Working copies

A working copy is a separate checkout in co:op where a task changes code. The page shows each worker’s available space, what cleanup will do next, and why a copy is kept. Uncommitted changes are retained. Committed work can be cleaned up once it is safely published in a draft pull request, or after an operator chooses to discard it.

When cleanup stops, the row says why. Resume cleanup tries the same step again. Discard unmerged throws away commits that were never merged and keeps uncommitted changes. Both ask first. A worker that is full stops taking new copies until space frees up.

Usage and cost

Usage covers every model call, including routing messages, replies, investigations, tasks and background learning, over the last day, week, month or all time. Tables break it down by model, channel, repository, kind of work and person, and each row opens the requests behind it.

Cost uses the amount the model provider reported. When a provider reports tokens but no cost, Ryker estimates it from your model prices and lists the rates it used; on a timeline, a cost marked ≈ includes an estimate. When nothing was reported, the row says “Not measured”, never $0.

Chat

Use Chat at /conversations to talk to Ryker in your browser. It supports the same investigations, tasks, memory, schedules and follow-ups as Slack. Each conversation works in one environment, starting with the default. You can attach up to two files, 8 MiB in all, edit or delete your own messages, and react to replies.

Every message links to its timeline. An incident opened from Chat is a real investigation without a Slack room. The browser never talks to a model provider or to co:op directly.

Integrations and settings

Each integration has its own page to connect, repair or disconnect it, and each checks what you paste before saving it. The Slack page also chooses who can manage Ryker, how it behaves in channels that have not chosen, and how incident rooms are named. The GitHub page decides whether Ryker may open pull requests.

Settings hold the Models for each kind of work (routing, conversation, standard and deep work, code changes, scheduled runs, incident rooms and learning), Data retention, Model prices, Weekly report, Access, and Advanced: where work runs, what each kind of work may do, and whether tasks that change code can run right now.

Each section saves on its own, and a draft survives a refresh. If someone else saved first, the page shows what is saved now before you save over it. A saved setting and the setting the running service uses are shown as two separate facts.

Where changes are controlled

Use the console for Ryker’s work and settings. Infrastructure changes still go through Emisar’s policy and approvals, and your team reviews and merges code changes. Worker policies and product prompts are maintained in code and configuration, reviewed in git.

For a quick check from Slack, App Home shows open work and anything waiting for you. The console gives you the full records and installation settings.
