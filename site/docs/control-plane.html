The control plane

Every request has a timeline, and the timeline is on a web UI served by Ryker itself, on your host, over loopback. This is where “it shows its work” stops being a slogan and becomes a page you can open.

What it is

The control plane is served by the Ryker service at http://127.0.0.1:4321, and it binds to loopback by default. There are no accounts, roles or invitations: on loopback, reaching the machine is the check. Reach it from the same machine or through an SSH tunnel. To let other people in, publish it only through Cloudflare Access or Tailscale Serve, which decide who reaches it; everyone who does can see and change everything in the install.

  • Changes ask first. Every action that retries, discards, pauses or deletes something asks you to confirm before it runs, and writes its change and its audit record together.
  • Secrets never render. A credential shows only as configured, missing or unusable.
  • No external assets. No CDN fonts, no analytics, no telemetry. Its scripts come from Ryker itself, and it renders with the network off, so nothing about production work leaves the machine.
  • Nothing here changes infrastructure. Emisar remains the only path for that.

Every page carries How this page works: its own help, written for someone who has never seen Ryker. Filters are part of the address, so a filtered list is a link you can paste into an incident thread.

Detail pages hang off these: one request’s timeline, one conversation, one incident room, one schedule, one channel, one failure. While required setup steps are open, Setup stays in the sidebar as a way back.

A request’s timeline

The timeline is the centre of the product. It is one request from start to finish, in the order things happened, in four stages: Intake, Routing, Work and Answer. The top says where the request stands, how long it took, what it cost, and what it is waiting for, if anything.

Intake
The message that started it: what Ryker extracted, the input as received, and the original message.
Routing
The channel settings and rules that applied, and the decision Ryker made, with its reason. A check that never ran says “Not checked”, never “No”.
Work
The worker and working copy it ran on, the exact briefing sent to the model, including what was left out to fit, the answer that came back, each check on that answer, and every tool the model used.
Answer
What was delivered, and where.

Background learning and cleanup that followed come after the answer, at their own recorded times. Every card has a link to itself, so you can share the exact step. History is bounded and says so: earlier activity loads a page at a time, and nothing is dropped or shown twice.

What was not recorded says so

A step Ryker did not record reads “Not recorded”, never a zero and never a guess rebuilt from today’s settings. A panel that looks live and is not would be worse than no panel at all.

Failures

The Failures page lists work Ryker could not finish on its own, newest first. Affects people comes first: someone is still waiting for a reply, an update or a result. Housekeeping is cleanup nobody waits on.

Each row says what stopped, who it affects, why Ryker stopped trying, and whether a retry should work: Retry should work, Needs you, Fix needed first, Retry won’t help, or Retrying on its own. A row has a button only when pressing it can help, and says what the button does before you press it. When something else has to change first, such as a token or Ryker’s place in a Slack channel, the row links to where to change it.

A failure’s own page tells the whole story: what happened, what it affects, what Ryker already tried, and each thing you can do, recommended first, including what happens if nobody acts. Ryker retries most things several times before it lists them, and an item leaves the list once its work finishes.

Working copies

A working copy is a checkout Ryker makes while a task works on code. The page shows the space each worker has, what cleanup will do next, and why anything is kept. Ryker removes a copy on its own once that is safe, and keeps one with uncommitted changes or commits that were never merged.

When cleanup stops, the row says why. Resume cleanup tries the same step again. Discard unmerged throws away commits that were never merged and keeps uncommitted changes. Both ask first. A worker that is full stops taking new copies until space frees up.

Usage and cost

Usage covers every model call, including routing messages, replies, investigations, tasks and background learning, over the last day, week, month or all time. Tables break it down by model, channel, repository, kind of work and person, and each row opens the requests behind it.

Measured and zero are different. Cost is what the model provider reported. When a provider reports tokens but no cost, Ryker estimates it from your model prices and lists the rates it used; on a timeline, a cost marked ≈ includes an estimate. When nothing was reported, the row says “Not measured”, never $0.

Chat

Chat, at /conversations, is a direct conversation with Ryker without Slack, and a real one: the same pipeline, and the same answers, investigations, tasks, memory, schedules and follow-ups as a Slack channel. Each conversation works in one environment, starting with the default. You can attach up to two files, 8 MiB in all, edit or delete your own messages, and react to replies.

Every message links to its timeline. An incident opened from Chat is a real investigation without a Slack room. The browser never talks to a model provider or to Coop directly.

Integrations and settings

Each integration has its own page to connect, repair or disconnect it, and each checks what you paste before saving it. The Slack page also chooses who can manage Ryker, how it behaves in channels that have not chosen, and how incident rooms are named. The GitHub page decides whether Ryker may open pull requests.

Settings hold the Models for each kind of work (routing, conversation, standard and deep work, code changes, scheduled runs, incident rooms and learning), Data retention, Model prices, and Advanced: where work runs, what each kind of work may do, and whether tasks that change code can run right now.

Each section saves on its own, and a draft survives a refresh. If someone else saved first, the page shows what is saved now before you save over it. A saved setting and the setting the running service uses are shown as two separate facts.

What it will not become

  • Multiple users, accounts, or roles.
  • A place to edit prompts or the policies workers run. Those are code and configuration, reviewed in git.
  • Anything that changes infrastructure. Emisar remains the only path.
  • A replacement for the Slack App Home.
