Ryker access, privacy and data

Run Ryker on infrastructure you control. Choose its repositories and tools, and understand where the work and its data go.

What stays on your host

Ryker stores its requests, work history, memory, pending replies and integration credentials in your PostgreSQL database. Credentials are encrypted with keys generated at installation. Your backups need both the database and those keys.

The bundled co:op worker runs model sessions and repository tools in containers with separate working copies. Its Docker daemon is private to the worker; model containers do not use your host’s Docker socket.

Using a hosted model sends context to that provider. Prompts can include messages, repository content, retrieved memory and tool results relevant to the work. Self-hosting Ryker gives you control of its stored state; it does not make a hosted model run locally. Choose your model account and provider terms accordingly.

Connected services also receive the requests Ryker makes to them. Slack carries replies, GitHub carries code and review activity, and Emisar executes and records infrastructure actions. Voice transcription and search-by-meaning models included with the default installation run on your host.

Who can ask it to work

Slack members
Active full members can ask questions and confirm code tasks. Guests, Slack Connect users, bots and deactivated accounts cannot authorize those actions. Configured app alerts have their own channel setting.
Slack operators
Manage channel behavior, incident controls and saved automation. They can also request a console sign-in link. Slack permissions.
GitHub collaborators
Need write or admin access to request work on a repository through GitHub.
Console users
Everyone signed in has full control of the installation. There are no separate console roles. Invite people who should have that access.
Emisar approvers
Approve infrastructure actions according to Emisar’s policy. Being a Slack operator does not itself grant this role.

Keep the console bound to loopback, or use a tunnel or HTTPS reverse proxy for remote access. See network access and console sign-in.

What Ryker can change

An environment selects the repositories and optional Emisar account a conversation can use. Code tasks write to one permitted repository; other repositories remain read-only context. Draft publication is a separate setting, and your team controls merging and releasing code.

Emisar checks the runner access of the person or service account behind Ryker’s API key, then applies the policy for that runner. Allowed actions can run; actions requiring review wait for an authorized approver; denied actions cannot run. A conversation or a remembered instruction cannot expand that access.

The GitHub App’s private key stays with Ryker. For authorized publication, the trusted worker receives a short-lived token for the repository, kept outside the model’s sandbox. Slack, Emisar and webhook credentials stay with Ryker. The worker reference explains the boundary.

Containers and policy checks limit access, but the installation host remains trusted. Protect host access, the database, generated keys and backups as you would the connected repositories and systems.

What it remembers

Background learning is on by default. It can learn from retained conversations even in channels where Ryker only observes. Turn it off under Memory › Learning if you do not want that behavior.

You can review and forget saved facts, learned topics and guidance in the console. Private Slack content is checked against the current audience before recall; knowing something from a private channel does not make it available everywhere.

Conversation memory lasts 90 days by default. Global facts have no automatic expiry, and active work can keep related history longer. Review the full memory rules and retention settings when choosing how long to keep data.

Review a request

Open Activity to follow a request through its model calls, tool activity, checks and reply. A proposed action, an approval, and the observed result are separate records. Missing checks and missing cost measurements remain visible.

Backups include credentials and the keys needed to decrypt them. Keep a protected copy away from the host and follow the backup and restore instructions.

Report a vulnerability

Use the repository’s security policy for vulnerability reports. Keep credentials, private messages and customer data out of public issues.
